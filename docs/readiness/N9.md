# N9 — Design constraints and per-variable values (M5, part 1)

State: implemented and tested (PR pending, 2026-10-28); the acceptance test below is Hoseung's.

## What was wrong

Layer: evidence. The framework could check only two constraint forms: a true/false test on the charter's values and a
linear condition on the decision variables. A rule on the design that is not linear (a minimum gap between fins, an
aspect ratio, a conditional rule) had no checkable form, so it lived in the evaluator or stayed words, and nothing kept a
method from spending evaluations on designs that break it. A declared problem also took one list of permitted values for
all its discrete variables and one representation for all its variables, so a whole number of fins beside continuous
widths had to be written as a continuous variable that the evaluator rounds (the `evaluator.mixed_values` workaround).
Invariant: INV-N9-1, INV-N9-2 (added, in `docs/invariants/N9.md`).

## Checked

- `tests/test_design_constraints.py` (8 tests): on a finned heat sink, a minimum-gap rule and an aspect-ratio rule refuse
  designs that break them and accept the others, with each instance's own thresholds; a whole number of fins and
  continuous widths canonicalize each by their own values, and discrete variables with lists of their own are checked
  each against its own; a charter with mixed values compiles with no `evaluator.mixed_values` finding, and one that needs
  neither keeps the schema it had; `random` proposes only feasible designs, a binary method without constraint support is
  refused, and `enumerate` visits only feasible candidates; a function method's `problem.feasible()`; the findings on a
  design expression; vectors in the expression language; an installed library that drops a design constraint or a
  variable's values differs from the charter.
- `frontend/tests/charter.spec.ts` "the constraints show their form" (Playwright): the Constraints table with a design,
  a linear and a qualitative rule.
- `tests/test_problem_charter.py`: the retired `evaluator.mixed_values` test is removed; the rest pass unchanged.
- The full suite (counts in the PR).

## Not done

- Outcome constraints (a condition on the metrics an evaluator reports) are N10. Problem-owned candidates (several
  orders, assignments, graphs) are N12.
- A design constraint reaches only a declared problem's schema. On an installed problem the charter checks it but the
  problem's own schema does not carry it; a warning says so.
- The plug-in methods that propose binary masks (hill climbing, annealing and the others) declare no constraint support,
  so they are refused on a problem with a design constraint, as they already were with a linear one. `swap_search` too.
- A design constraint is checked whole on every candidate; there is no partial check a method could use to prune a
  partly built design.
- `random` gives up after 10,000 infeasible draws in a row, as before; a design rule met by almost no design needs a
  method that builds feasible designs.

## Acceptance test

1. Start the app, create a campaign and describe a problem with a whole-number variable beside continuous ones and a
   rule on the design that is not linear, for example: "a heat sink on a 50 mm base with between 2 and 12 fins, each
   0.5 to 5 mm wide and 5 to 50 mm tall; fins must stand at least 1.5 mm apart, and a fin may be at most 12 widths
   tall; minimise the thermal resistance".
2. Open the Charter page. The number of fins is a discrete variable with its values (2 to 12), beside the continuous
   width and height, and there is no check asking to rewrite them as ranges. Under "Constraints" the gap rule and the
   height rule each read "design: a condition on the design, checked on every candidate", with their condition.
3. Change a threshold so no design can meet a rule (for example a gap of 60 mm, wider than the base): a warning says
   none of the random designs meets it. Put it back.
4. Confirm the charter and run "Uniform random" on it once its evaluator exists. Every evaluated design has a whole
   number of fins and meets both rules; no evaluation is spent on a design that breaks them.
