# E2 — The installer accepts problem libraries

State: implemented and tested (PR #36, 2026-10-27); the live check is Hoseung's.

## What was wrong

Layer: none: a missing capability, not a failure at a layer. Decision 1 has the coding agent write the scoring function
into its library, and the installer refused any library without an optimizer entry point.
Invariant: INV-E2-1 (new).

- `Installer.prepare()` refused a library whose `pyproject.toml` named no `optimization_framework.optimizers` entry point,
  so a library that provides only a problem (its evaluator) could not enter the lab, and one that provides both had its
  problem installed without any record of it.
- Nothing checked that a library's ids were free. A problem id another package already provides would leave the first one
  loaded in the registry (E1's "Not done"); a duplicate optimizer plug-in name or method id stops the plug-in listing.

## What changed

| Change | Where |
|---|---|
| A library may name `optimization_framework.optimizers`, `optimization_framework.problems`, or both; one with neither is refused, naming both groups | `agents/library_install.py` `Installer.prepare()` |
| Before uv runs, a problem id, optimizer plug-in name or reported method id that another installed distribution provides is refused: "problem <id> is provided by <distribution>". The lab's own (its root project, its built-in methods) counts as another; the library's own earlier version does not. Balsamic's own install records the refusal as a failed install and tells the lead, as other refusals | `Installer._refuse_clashes()`, `providers()` |
| Each install records `problem_entry_points`, `problems_added` and `missing_problems` (declared problems the registry does not list after the sync) beside the methods. The notice names the problems, and asks the lead to bind proposals only when the library provides methods | `Installer.install()`, `added()` |
| The registry's `refresh()` compares with what is installed at once, so the install reads what its own sync added instead of a listing up to a second old | `evaluation/registry.py` `ProblemRegistry.refresh()` |
| The monitor's install row, the workspace timeline and the Implementations card name the problems an install added | `src/balsamic/monitor/rows.py`, `agents/development_timeline.py`, `frontend/src/hypotheses/Implementations.tsx` |
| The notice names what was added through `added()`, and adds B4's binding line only when the library provides methods. B4's binding tests deliver the lab's own methods as a library's, which the clash check now refuses, so they skip that check | `Installer.install()`, `tests/test_automatic_binding.py` |
| New register row | `docs/invariants.md` INV-E2-1 |
| The plug-in guide says a library may provide problems, and what a clash does | `docs/optimizer-plugins.md` |

## Checked

- `tests/test_library_install.py`: a problems-only library installs and records `problems_added`, with a notice that
  names the problem and asks for no binding; a problem that does not load is listed in `missing_problems`; a library with
  both groups records methods and problems; one with neither is refused before any uv command; a problem id, plug-in name
  or method id another package provides (another library, the lab's own problem, a built-in method, a method of
  grating-mask-search) is refused before any uv command, with `pyproject.toml` untouched, and Balsamic's own install
  records it as failed; the library's own earlier version is no clash; `providers()` names the lab as the distribution of
  its own `bounded_continuous`. The existing install tests pass unchanged.
- `tests/test_problem_registry_installs.py`: `refresh()` lists an install at once, where `ids()` waits up to a second; a
  frozen registry's `refresh()` does not change.
- Full suite with `-n 4`, the launcher's tests as user `claude`, `npx tsc -b` and the Playwright suite: counts in the PR.

## Not done

- Tasks do not adopt the library's problem yet: an existing campaign's tasks keep their declared problem and evaluator
  until E3 recognizes the installed problem in the charter and E4 recompiles the tasks.
- `missing_problems` means "not listed by the registry after the sync"; the installer does not import the problem in the
  server to check that it resolves. A problem that is listed but fails to load shows when it is first used.
- Method ids are known before the install only from the coding agent's delivery report; a method the report leaves out
  is not checked for a clash before uv runs, and the plug-in listing still refuses a duplicate after it.

## Acceptance test

Needs the app running, and a coding workspace that delivers a library providing a problem (ask the lead for one in a
campaign whose charter declares a problem, e.g. "write the scoring function as a library that provides this problem").

- [ ] E2: a library that provides a problem installs, and the problem is listed without a restart
  1. Let the coding workspace deliver; Balsamic installs the library by itself (or press Install on its card).
  2. Go to Hypotheses → Implementations and look at the workspace's card.
  Expect: the install is shown as installed, with "problems <the problem's id>" (and "methods …" only if the library also
  has methods). The lead's notice names the problem.
  3. Without restarting Balsamic, start a new campaign.
  Expect: the problem the library provides is offered among the problems to choose from.
- [ ] E2: a problem that is already installed is refused
  1. Have the coding agent deliver a library that provides a problem with an id the lab already has (e.g.
     `bounded_continuous`).
  Expect: the install fails before anything changes, and the card says "problem bounded_continuous is provided by …".
  The lab's own problem keeps working.
