# C1 — Permutation representation

State: implemented and tested (PR #9, 2026-10-27); not checked live.

## What was wrong

A candidate could be binary, discrete or continuous, and nothing else. Baking order (choose the order of 8 bakes) had no
honest encoding: written as discrete values, the built-in `random` drew vectors with repeats and gaps, which are not orders,
and every run failed or wasted its evaluations on candidates the evaluator had to refuse.

## What changed

| Change | Where |
|---|---|
| `CandidateSchema.representation` takes `permutation`: an order of the items 0 … dimensions−1 (indices into the instance's data), each once. It takes no bounds, values or linear constraints; `canonicalize` refuses a repeat, a gap or an out-of-range item and returns ints | `contracts/problems.py` |
| `InferenceDescriptor.representations` and `DecisionVariable.representation` take it | `contracts/capabilities.py`, `contracts/problem_charter.py` |
| Charter checks: an order needs a one-entry shape (`variable.shape`) and no bounds or values (`variable.permutation`); a linear constraint on it is refused (`constraint.permutation`); a declared problem takes one order (`evaluator.permutations`). `manifest()` builds the permutation schema; `from_setups()` maps it back with a one-dimensional shape | `problem_charter/charter.py` |
| `random` lists permutations and `BoundedSearch.ask()` draws `rng.permutation(n)`; the ask/tell adapter hands observed orders to the method as integers. The registry's binary-only branches route an order to `BoundedSearch` and refuse an inline `initial_design`, as for any non-binary domain | `optimizers/lifecycle.py`, `optimizers/registry.py` |
| The Charter page reads an order as "an order of N items", with no bound inputs | `frontend/src/note/CharterPanel.tsx` |
| Formulation guidance: an order or a ranking is a permutation, not discrete values | `problem_import/guideline.md`, `src/balsamic/procedures/problem-formulation/SKILL.md`, `agents/roles/methodology_specialist.md`, `docs/problem-setup.md` |

## Checked

- `tests/test_permutations.py`: `canonicalize` accepts a rearrangement (lists, arrays, whole floats) and refuses a repeat,
  a missing item, an out-of-range item, a fraction and a boolean; a permutation schema refuses bounds, values and
  constraints; an 8-bake charter has no blocking finding, compiles to `permutation` × 8 with no bounds and maps back; a
  two-dimensional shape, bounds, a linear constraint and two orders are each a blocking finding, and an order mixed with a
  continuous variable is still `evaluator.mixed_variables`; `random` proposes only valid orders, keeps its best as integers,
  and `hillclimb` says it requires binary candidates.
- `frontend/tests/charter.spec.ts`: an order shows "an order of n_seats items" with no bound inputs.

## Not done

- No method searches orders yet; `random` is the only one. Swap and insertion moves are C2; `replay` and `evaluate_asset`
  still list only the three other representations (C2).
- Not checked live: baking order's charter has not been rewritten as a permutation on the dev stack.

## Acceptance test

1. Start the app and open a campaign whose problem is an order: baking order (the order of 8 bakes to minimize total
   tardiness), or any problem that asks for an order or a ranking.
2. On the Charter page (the problem note's Charter tab), ask the formulator to write the decision as an order of the bakes.
   The Variables table should show the variable as `permutation`, read "an order of n_bakes items" (with "n_bakes = 8" where
   its meaning is shown), and offer no lower or upper bound fields. No blocking check should be about that variable.
3. Ask the formulator to add a lower bound to the order, or a linear limit on it. A blocking check should say that an order
   takes no bounds, or that the lab cannot enforce a linear condition on an order.
4. Confirm the charter, install its task and run "Uniform random" (`random`) on it for a few dozen evaluations. On the
   Experiments page every evaluated design should be an order of 0 to 7 with each number once, and none should be marked
   as an invalid candidate.
5. Look at the method list for the same task: the binary-only methods (hill climbing, annealing and the like) should show as
   not available, with "requires binary candidates".
