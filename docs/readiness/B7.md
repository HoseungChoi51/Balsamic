# B7 — The lead's instructions and the supervision procedure

State: implemented and tested (PR #58, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

Layer: prompt. B1 to B5 made "implement and compare" one go-ahead after which Balsamic installs, binds and starts the
approved runs, but the texts the lead reads still described the old path.
Invariant: INV-28 (unchanged: the ratchet holds after the added line).

- **The supervision procedure told the lead to bind and hand over the runs.** Step 4 of `implementation-supervision`
  said "Bind each proposal to its method with `implementation.bind_builtin` and hand the runs to the experiment
  operator", although B4 binds after each install and B5 starts the approved runs.
- **Nothing told the lead the request is one go-ahead.** The shared instructions said to file a compute request before a
  coding workspace and before long runs, but not that one request covers the workspace, the proposals and their runs, so
  a lead could ask at each step. They still said "Never enlarge an allocation", left from before B3 made the
  implementation allocation an optional ceiling.
- **The method catalog named the lead for every unbound proposal.** Its next action "Bind … (implementation.bind_builtin)"
  and a proposal's readiness ("Bind this proposal to its method … to run it") appeared even while Balsamic was about to
  bind it, and gave no reason when Balsamic had left it.
- **`campaign_inspect.capabilities`** said a library is "installed by the researcher" and "run by binding the proposal".

## What changed

| Change | Where |

(Its allocation paragraph was already gone with B3) | `src/balsamic/procedures/implementation-supervision/SKILL.md` |
| `binding()`: Balsamic is the next step for an unbound proposal while its install's post-install step has not run; the lead only for a proposal that step skipped, with B4's reason, or one no recorded install covers. ## Not done

- Whether a real model now files one request and binds nothing is measured by the live eval S18, not by the scripted run
  (the script plays the right behaviour; it checks the grader and the plumbing).
- The lead's contract still says the experiment operator starts runs; that stays true for runs no plan lists.
- Planned runs naming only an algorithm (no proposal) are still started by an agent (B5's "Not done").

## Acceptance test

Use a campaign with the lead on, with the problem defined, where the lab has neither of two methods you will name.

1. Write only: "Implement a pattern search and a cross-entropy method and compare them: 2 seeds each, 5 minutes per run."
   Do not mention compute requests or runs.
2. The lead records the two proposals and puts one approval card in the inbox. The card names the coding workspace and the
   4 runs (2 proposals × 2 seeds, 5 minutes each). No second card follows asking to bind, to raise an allocation or to
   start runs, and the lead does not ask you to run any command.
3. Approve it. Wait for the coding agent to deliver: Balsamic installs and binds by itself, and the 4 runs appear on
   Experiments, started by Balsamic, without you writing anything.
4. On Hypotheses → Implementations, the method's row shows no "Bind … " step for the lead.
5. When all 4 runs end, the lead writes the comparison once.
