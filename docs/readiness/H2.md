# H2 — A harness adapter, with Pi as the harness

State: implemented and tested (2026-10-27, on `main` with H5 merged in); J4's headless run and the checks on a live
workspace are Hoseung's (see the acceptance test).

## What was wrong

Layer: none. No failure is fixed; this adds the seam that H7's headless commissions need. Nothing could run the coding
agent without its terminal UI. `start.sh` wired the box to one way of running Pi (its TUI in tmux, with the extension as
the only bridge), and nothing pointed Pi at H1's MCP server.
Invariant: INV-H2-1, INV-H2-2 (added); the pin of INV-24 now also covers the harness setting (row unchanged).

## What changed

| Change | Where |
|---|---|
| The harness adapter, a dependency-free Node module in the box. An adapter configures the harness for H1's MCP server, gives the command tmux runs, gives one headless invocation, maps one record of the harness's stream to bridge events, and stops a run. `HARNESSES` holds only `pi`; any other name is refused with one text | `deploy/implementation-workspace/harness.mjs` |
| Pi's adapter. At each start it writes the `balsamic` server (`balsamic-workspace mcp`, local stdio) into `~/.pi/agent/mcp.json` and keeps the researcher's other servers. `checkpoint` and `submit` are hidden there, because the extension already gives Pi `campaign_checkpoint` and `campaign_submit`, so Pi gains `ask`, `check` and `evidence`. Its stream mapping is the extension's own | same file, `pi.configure()`, `pi.map()` |
| Two modes. **tui**: tmux runs Pi's terminal UI with the extension, the same command as before. **headless**: tmux runs the adapter's runner. It reads the host's commands from the bridge as the extension does and sends an accepted receipt for each. It runs each message as one `pi --mode json` on the same session file, with the instruction on stdin and steering messages ahead of follow-ups, and maps the JSON stream (split on LF only, as Pi's docs ask) to `agent_start`, `message` with its usage, `tool` and `agent_settled`. It marks the instruction `completed` when Pi settles. A pause or stop interrupts the running instruction (`interrupted`, closed with `agent_settled`). A run that fails is reported as `harness_error` with its stderr (`failed`). Instructions already run are kept in `/work/sessions/pi-delivered.json`, so a restarted box does not run them again. Ctrl+C in the attached pane does not end the runner | same file, `runHeadless()`, `records()` |
| Headless, the extension gives only its tools; the runner reports the events and delivers the commands | `agent-harness/extensions/implementation.ts` |
| `start.sh` reads the harness setting (`BALSAMIC_HARNESS`, `BALSAMIC_HARNESS_MODE`) and refuses any other harness or mode (exit 78, with the text) before it touches anything. It then has the adapter configure the harness and give tmux's command. The image installs the adapter; the host also mounts the repository's copy read-only, as it does the extension and the CLI | `deploy/implementation-workspace/start.sh`, `Dockerfile`; `agents/development_runtime.py` `DockerWorkspace.start()` |
| The harness setting per workspace, `harness: {name, mode}` on the record. It comes from the create request's `harness` (only `pi`) and `harness_mode`, else the lab's `GRATING_DEVELOPMENT_HARNESS_MODE` (the launcher's `development_harness_mode`), else `tui`. A record from before H2 runs Pi's TUI. The host refuses any other harness when the workspace is requested and again before it starts a container. A request that names `pi` hashes as one that names nothing, so existing request keys still match | `agents/development_runtime.py` `harness()`, `harness_refusal()`; `agents/development.py` `WorkspaceCreate`, `request_hash()`, `create()`; `scripts/manage_servers.py` |
| `harness_error` counts as an error on the card (its last error) and shows in the workspace's history | `agents/development.py` `ERROR_EVENTS`; `agents/development_timeline.py` |
| The coding eval can run headless: `--harness-mode headless` sets the lab's mode and records it in the results and the baseline, written as `<commit>-headless.json` beside the TUI baseline | `scripts/run_coding_evals.py`, `evals/coding/README.md` |
| A recorded Pi stream, a fake `pi` for the tests, and the description of the adapter | `tests/fixtures/harness/`, `docs/pi-implementation-workspace-plan.md` |

The seam for another harness (decision 8) is one more entry of `HARNESSES` with its own `configure`, `command`,
`invocation`, `map` and `stop`. It would be opted into per workspace through the same setting, run on the researcher's own
credentials mounted read-only, and add only its model endpoint to H5's egress allowlist. The MCP server is local, so the
adapter adds no host to the box's egress. No other harness is added.

## Checked

- The recorded stream, `tests/fixtures/harness/pi-json-stream.jsonl`: one real headless run of Pi 1.0.4 (the harness's
  pinned version) against a scripted OpenAI-compatible endpoint, in the box's own setup. The extension gave its tools and
  the adapter configured the MCP server. It has four assistant messages and three tool calls (`bash`,
  `campaign_checkpoint`, `mcp__balsamic__evidence`); only this machine's paths were rewritten to the box's. In the same
  run the model's tool list held `campaign_checkpoint`, `campaign_submit` and `mcp__balsamic__ask`, `check` and `evidence`,
  without the two hidden twins. The checkpoint reached the bridge from the extension, which wrote nothing else.
- By hand on the same endpoint, not in the suite: the headless runner on real Pi delivered a host command and wrote
  ready, the receipts, `agent_start`, four `message` events with their usage, three `tool` events and `agent_settled`.
  Pi's TUI, started in tmux from the adapter's command, delivered a researcher's command through the extension and wrote
  the same events. Its `mcp__balsamic__evidence` call listed the evidence.
- `tests/test_harness_adapter.py` (7 tests):
  - In both modes the fake `pi` replays the recorded stream: headless on stdout after reading its instruction on stdin,
    and as the TUI into the real extension, which delivers the instruction. The workspace record gets the stream's events
    in order between the instruction's accepted and completed receipts, the usage as recorded (4 calls, 6528 input, 220
    output, 3072 cache read), status idle, the last assistant text, and one "Worked · 3 tool calls" entry in the history.
  - Both modes leave the same events.
  - A harness other than `pi` is refused with the same text at create (nothing recorded), at the host's start (no docker
    command run), by `start.sh` (exit 78, `HOME` untouched) and by the adapter's three commands; another mode is refused
    too.
  - The container gets `BALSAMIC_HARNESS` and `BALSAMIC_HARNESS_MODE` and the adapter mounted read-only. The lab's mode
    applies to new workspaces, and a record from before H2 runs Pi's TUI. Naming `pi` keeps the request's hash.
  - `configure` keeps other MCP servers and hides the twins, and leaves an `mcp.json` it cannot read untouched. The TUI
    command is the one `start.sh` ran before.
  - A failed headless run is the workspace's last error and a "The coding agent's run failed" entry in its history.
- `agent-harness/test/harness.test.mjs` (6 tests):
  - On the recorded stream, the extension's handlers and `pi.map()` write identical bridge events.
  - Headless, the extension registers its two tools and nothing else.
  - The runner runs a steering message before earlier follow-ups. A pause interrupts the running instruction
    (`interrupted`, then `agent_settled`), the queue goes on, and a restarted runner runs nothing again.
  - A failing run gives `harness_error` with its stderr, `failed` and `agent_settled`, and a harness that cannot start
    does the same.
  - The stream is split on LF only: a U+2028 inside a string and a record cut across chunks are kept.
  - Another harness or mode is refused with the text.
- `tests/test_invariant_pins.py`: the network test still holds, and now also checks that `start.sh` reads the harness
  setting and starts it through the adapter, that it has no `iptables`, `setpriv` or `sudo`, and that the setting never
  reaches `network.sh`.
- `tests/test_coding_evals.py`: the fake run, now with `--harness-mode headless`, records the workspace's harness as
  `pi`/`headless` and the baseline's `harness_mode`, and restores the lab's setting.
- `tests/test_server_launcher.py`: `development_harness_mode` reaches the services, a variable left in the calling shell
  does not, and another value is refused.
- The harness suite, the development-workspace tests and the full Python suite pass (counts in the PR).

## Not done

- **The live checks are Hoseung's**: J4 run headless and recorded beside the Phase 2 baseline, and the acceptance test
  below. Docker is not available in the cloud session. The image runs Pi 1.3.0 and the recording is from 1.0.4, the
  harness's pinned version: the live run checks the stream and the MCP configuration on 1.3.0.
- **The image must be rebuilt** (`docker build -t grating-implementation-workspace:pi-1.3.0 deploy/implementation-workspace`),
  as for H5's `network.sh`: `start.sh` is part of the image. Until then a box runs the old `start.sh`, Pi's TUI whatever its
  setting. A container created before H2 keeps its image until it is removed.
- **Headless runs cannot be steered mid-run.** `pi --mode json` takes no input while it runs, so a steering message waits
  for the running instruction and then runs before queued follow-ups. Pi's RPC mode could steer mid-run; the roadmap names
  JSON mode.
- An interrupted instruction is not run again, as in the TUI, where the extension aborts it. A runner that crashes is not
  restarted, as Pi's TUI is not today.
- `harness_error` reaches the card and the history, not the lead or the agent that opened the workspace (no notice). H7
  may add one for commissions.
- No UI chooses the mode for one workspace: the HTTP API's `harness_mode` does, and the launcher's
  `development_harness_mode` sets it for new workspaces. The agents' `implementation_workspace_create` schema is unchanged,
  so no prompt text was added. The card does not show the mode.
- No other harness is added (decision 8).

## Acceptance test

Before: rebuild the coding-workspace image and restart the lab with coding workspaces on, as for any workspace change.

1. **Pi's terminal UI, as before.** In a campaign with the lead agent on, ask the lead to open a coding workspace for a
   proposal, and approve the go-ahead it asks for. On the Proposals page, open **Implementations** and find the workspace
   under **Coding workspaces**. Open its IDE: the **Pi implementation** terminal shows Pi's terminal UI, as before.
2. In **Message the coding agent**, write: "List your tools whose names start with mcp__balsamic, then call
   mcp__balsamic__evidence and tell me what it printed." Send it. The coding agent should name `ask`, `check` and
   `evidence` (not `checkpoint` or `submit`: it has those as `campaign_checkpoint` and `campaign_submit`) and list the
   evidence the workspace was given, or say none was given. The workspace's **History** should show the work.
3. **Headless.** Stop the lab, set `"development_harness_mode": "headless"` in the launcher file, and start it again. Open
   a coding workspace for another proposal as in step 1.
4. Without anyone attached, the workspace should work as before: its **History** fills with "Worked …" entries, the coding
   agent's checkpoints set its phase, and its questions reach the lead. In the IDE, the **Pi implementation** terminal shows
   the runner's log (each instruction, the assistant's lines, the tool calls), not Pi's terminal UI.
5. Write: "Reply with the single word headless." The **History** should show your message, then "Replied" with
   "headless".
6. While the coding agent is working, **Pause** the workspace. It should stop within seconds and show as paused.
   **Resume** it, then send a message: the agent should answer it, continuing the same session (it remembers the earlier
   work).
7. Back in the launcher file, remove `development_harness_mode` (or set `"tui"`) and restart: new workspaces open with
   Pi's terminal UI again; the headless one keeps its mode.

Phase 2 baseline, and `evals/coding/baselines/<commit>-headless.json` beside it. Commit the baseline file.
