# A4 — Checkpoints go to whoever opened the workspace, as notices

State: implemented and tested (PR #PRNUM, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

- **Every checkpoint woke the lead with raw JSON.** `_apply_event()` called `notify(record, key, json.dumps(payload))` for
  each `campaign_checkpoint`, progress lines included: 35 relay turns on `lead_2d-gratnig`, a third of the lead's turns
  (`docs/suggestions.md` S2).
- **They went to the lead whoever opened the workspace.** `create()` recorded `opened_by` but `notify()` always enqueued to
  the lead, so a workspace the implementation lead opened reported to an agent that had not asked for it.
- **They read as requests.** The text did not start with `NOTICE`, so the state block said "Turn: a request", and the turn
  continued whichever request happened to be latest, not the one the workspace was opened for.

## What changed

| Change | Where |
|---|---|
| `create()` records the request root of the opening turn (`request_root`, from `PiTools.assignment_origin`: the lead's own request, or the request a page agent was asked under) | `agents/development.py` `create()`; `agents/tools.py` `implementation_workspace_create` |
| Notices go to `opened_by.agent_id` while it is a live agent of this campaign (not stopped, completed or failed), else to the lead | `agents/development.py` `recipient()`, `notify()` |
| A notice starts with `NOTICE` and continues the workspace's request: the lead's through `enqueue(root=…)`, another agent's with the root in its run's origin | `agents/development.py` `notify()` |
| A checkpoint notifies only for a question, a new blocker (a different `blocker`, or entering the `blocked` phase); progress updates the record and the timeline only. Submissions, installs, host blocks, recoveries, the CPU allowance and the researcher's instructions notify as before | `agents/development.py` `_apply_event()` |
| A notice names what changed (the question with its id, the blocker, cut to 600 characters) and which part of `implementation_workspace_inspect` to read (`questions`, `checkpoints`, `submissions`, `installs`, `validation_envelopes`), not the JSON | `agents/development.py` `notify()`, `excerpt()`; `agents/library_install.py` |
| A new invariant row, INV-29, next to INV-05 | `docs/invariants.md` |

## Checked

- `tests/test_pi_development_workspaces.py`:
  - `test_a_workspace_opened_by_the_implementation_lead_sends_its_notices_there_continuing_its_request`: the question goes
    to the implementation lead, not the lead; it starts with `NOTICE`, names the question and `questions`, carries no
    JSON; its origin's root is the opening request; the state block reads "Turn: a platform notice, not a request". Once
    the opener is stopped, the next blocker goes to the lead, still continuing that request.
  - `test_progress_checkpoints_send_no_notice_and_a_question_or_a_new_blocker_sends_one`: five progress checkpoints in
    one phase send none while the record and timeline follow them; a question sends one; the same blocker twice sends one;
    a different blocker sends another.
  - `test_the_lead_opening_a_workspace_records_the_request_its_turn_works_on`: the tool passes the lead's request root and
    the opener.
- The tests importing the changed modules (`scripts/test-changed`): 158 passed. The full suite: see the PR.

## Not done

- The replay on the `lead_2d-gratnig` records (S2's third "Done when") is not part of A4's "Done when" and was not run:
  the records are not in the repository.
- Phase changes other than into `blocked` (orienting → implementing → testing) wake no one; the researcher follows them
  on the Implementations page.
- The researcher's own messages to the coding agent still notify the lead ("The developer directed…"), as before.

## Acceptance test

Start the app with coding workspaces on, on a campaign whose agent team is running.

1. In the main thread, ask the lead to implement a proposal in a coding workspace, and give the go-ahead it asks for.
2. While the coding agent works, keep the Implementations page open beside the thread. The page should show the coding
   agent's progress (phase, done, remaining, estimate) changing; the thread should not get a message from the lead for
   each of those steps.
3. If the coding agent asks a question or reports a blocker, one message should follow in the thread, saying what was
   asked or what blocks it, without a block of raw JSON. When it delivers, and when Balsamic installs the library, one
   message each should follow.
4. Those messages should continue your request: the thread stays on it, and no new request of yours appears.
5. Optional: on the Implementations page, ask the implementation lead to open the workspace instead. The question,
   blocker and delivery messages should then come from the implementation lead on that page, and the lead should not
   post about them in the main thread.

Expected: a handful of agent turns for the whole build (a question, a blocker, the delivery, the install), not one per
checkpoint.
