# F3 — Balsamic glue in the generated library

State: implemented and tested (PR pending, 2026-10-27); nothing to check live until F4 starts coding workspaces from
the generated library.

## What was wrong

Layer: none: a missing capability, not a failure at a layer.
Invariant: INV-F3-1 (new).

- F1's project ran on its own, but could not enter the lab: it had no problem adapter, no entry points, and nothing
  checked it against Balsamic's contract.
- F1's `methods.py` listed methods as `METHODS = {"id": function}`, which D2's `FunctionPlugin` cannot read: it lists
  methods from a `METHODS` literal (`{"id": {"name", "description", ...}}`) without importing the module. A filled F1
  project could not have been offered to Balsamic as it was.
- F1 refused permutation charters until C1 landed.

## What changed

| Change | Where |
|---|---|
| `scaffold(..., balsamic=True)` adds `<pkg>/adapter.py` and `tests/test_contract.py`, puts the charter in `data.py` (`CHARTER`), and gives `pyproject.toml` both entry points: the problem under the charter's problem id (a declared evaluator only; an installed one is another package's) and the methods under the package name. It refuses a charter that names no evaluator. Without `balsamic` the bytes are as before, apart from the changes below | `problem_charter/scaffold.py` `scaffold()`, `_pyproject()` |
| `adapter.py`: `problem_adapter()` and `method_plugin()`, importing Balsamic only inside them, so `import <pkg>` and `import <pkg>.adapter` work without it. The method plug-in is a `FunctionPlugin` with `MODULE = "<pkg>.methods"`, `REPRESENTATIONS` from `data.py`, and `problem(instance)` giving each method the library's own `Problem`. The library's objective and problem are imported inside `_code()`, so a frozen capture still follows them | `scaffold_files/adapter.py.tmpl` |
| `CharterProblem`: the problem adapter. Its definition and instances are `charter.manifest()` for the values a configuration gives, from `data.CHARTER`, so its id, schema, objective, metrics and fields are the charter's. A configuration field on a derived quantity must agree with what the charter computes. Its evaluator canonicalizes the candidate and returns `objective.objective(problem, candidate)`; a non-finite value is an error. The evaluator version is the revision and a hash of the package's code other than `methods.py`. A `data.py` whose charter no longer has its content hash is refused. A configuration that is none of the charter's instances gets a `Problem` of its own (`scaffold.instance_data()`) | new `problem_charter/library.py` |
| `tests/test_contract.py`: the library holds the charter revision; `compare_provided` finds no difference between the library's problem and the root `charter.json`'s (declared evaluators); `check_function` passes for each method. `pytest.importorskip("optimization_framework")` skips it where Balsamic is not installed | `scaffold_files/test_contract.py.tmpl` |
| `METHODS` is the literal D2 reads, in standalone projects too; `harness.methods()` maps each id to its function and says what is wrong with an entry. `compare` and `tests/test_methods.py` use it. ## Checked

- `tests/test_problem_charter_library.py` (12 tests): the files, entry points and `CHARTER` that `balsamic=True` adds, and
  the same bytes twice; the adapter imports only `data` at module level, and a frozen capture's import scan reaches the
  objective and the problem; an installed evaluator gives only the methods' entry point, and a charter with no evaluator
  is refused. With a filled objective and three methods, loaded from a temporary directory through the entry points in
  its own `pyproject.toml`: the registry resolves the problem without importing the objective, problem or methods
  modules; `compare_provided` finds no difference and the definition's version is the manifest's; `check_function` passes
  for every method; a method gets the library's own `Problem`; the evaluator returns the objective and refuses a candidate
  over the heater limit. A configuration that is no instance gets its own `Problem`; an unknown field is refused; a field on
  a derived quantity that disagrees with the charter is refused; the charter's findings call the installed library
  `evaluator.provided` with no mismatch; an edited `data.py` is refused. A permutation charter (baking order) generates, its
  library passes `compare_provided` and `check_function` for two methods, and evaluates an order's lateness. Both generated
  projects pass their own tests with Balsamic installed, the contract tests included; with Balsamic hidden the project's
  tests pass and the contract test is skipped. A `METHODS` of functions fails with what to write instead.
- `tests/test_problem_charter_scaffold.py` (F1's 9 tests) with `METHODS` as a literal.
- Full suite with `-n 4` and the launcher's tests as user `claude`: counts in the PR.

## Not done

- Coding workspaces do not start from the generated library yet (F4), and the F2 export stays the standalone project.
- The library's evaluator reports only the primary objective. The charter's metrics are listed in its instances, as the
  declared problem lists them, but a generated objective returns one number, so they are not computed.
- An instance's values that no evaluator field carries (the ovens' tray count) do not reach an installed problem: tasks
  of an installed problem take only the configuration and fidelity (E3). The contract test compares the charter's own
  values, as E3's check does.
- The problem's definition is computed by the installed Balsamic's `manifest()`. A Balsamic change to `manifest()` changes
  the definition's version, and a run frozen before it no longer resolves to the same problem.
- Balsamic gives a method `problem.values` but not an objective call on the problem (D1 names `problem.objective`): a
  white-box method imports `objective.objective`, as the template says.

## Acceptance test

None: F3 adds no screen and no step a user takes. It shows with F4, when a coding workspace starts from the generated
library and its delivery installs with the problem and its methods; until then, the tests above are the check.
