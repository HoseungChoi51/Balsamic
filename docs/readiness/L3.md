# L3 — Workspaces build on the latest version

State: implemented and tested (PR on branch `claude/project-thread-fcyj4d`, 2026-10-28); not checked live (see the acceptance test).

## What was wrong

Layer: prompt. Each coding workspace started from the blank library generated from the charter, so the coding agent never saw
the methods earlier campaigns built on the same problem and wrote them again, and its delivery was reviewed against the blank
library.
Invariant: INV-L3-1 (added).

## What changed

| Change | Where |
|---|---|
| When the library a workspace would generate (named by the charter's problem id) has an installed version, the workspace starts from the latest version's files (its commit in the library's repository, L2) instead; its record's `library` names the `base` (package, version, tag, commit, methods, problems). A workspace keeps the start it was prepared with: a later version does not change it, nor does a first version installed after it started from the generated library | `agents/development.py` `DevelopmentWorkspaces.based()`, `generated_library()` |
| The ticket says what the workspace builds on: TASK.md's "What you build on" lists the version, its methods and problems, and the rule (keep every method and what it does; a changed behaviour is a new method name; a changed scoring function is a new problem id; raise the version). The base's tests are among the acceptance tests ("base version"); the house rules say to add beside the existing methods | `agents/development_ticket.py` `build()`, `base_lines()`, `task()`, `house_rules()` |
| The review's diff is against the base version (`base_version`, `base_package`), and the install records it (`base_version`). Decision 9 holds against the base: its `charter.json` and data stay fixed | `agents/development.py` `diff()`; `agents/library_install.py` `base_of()`, `generated_changes()` (unchanged) |
| The researcher's own session clones the same start, a commit named after the base version | `agents/own_session.py` `start()` |
| The workspace card says "Builds on package <name> <version> (<n> methods)"; the install card says which generated files changed from the base | `frontend/src/hypotheses/Implementations.tsx`, `workspace.ts` |

## Checked

- `tests/test_library_base.py`: a second workspace on a problem with installed versions starts from the latest, its ticket
  lists the methods and the rule and the base's tests, and a later version does not change its start; the diff of a delivery
  that changed one file is that file, against the base; an edit of the base's data is refused; a problem with no installed
  version starts from the generated library and keeps that start.
- `frontend/tests/implementations.spec.ts`: the card says what the workspace builds on.
- Full runs at the PR's head: see the PR.

## Not done

- A workspace builds on the library of its own problem only; a method of another problem's library is reused by binding it
  (L5), and split into a method library when a second problem needs it (L6).
- When the charter's problem differs from the installed one with the same id, the charter's check at adoption says so; the
  researcher gives the changed problem a new id (decision 25).

## Acceptance test

1. In a second campaign on a problem whose package is installed, approve a coding workspace.
2. On the Implementations page the workspace card says "Builds on: package <name> <version> (<n> methods)".
3. Open the editor: TASK.md has "What you build on", listing the existing methods and saying to keep them, to give a changed
   method a new name and to raise the version.
4. When it delivers, the review's diff shows only what it changed against that version, not the whole package.
