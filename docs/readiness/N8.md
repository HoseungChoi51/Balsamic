# N8 — Domain optimizers leave the core registry

State: implemented and tested (PR #46, 2026-10-27); the acceptance test is Hoseung's.

## What was wrong

Layer: none. No run failed; the core named a domain. The 2D deflector's six FLRL Fourier methods were built into the
core's optimizer registry: their descriptors and parameter schemas sat in `optimizers/fourier_specs.py`, and `create()`
imported `dqn_meent.flrl_optimizers` by name, so the generic framework depended on MEENT's package, against the plug-in
design the mask library already followed.
Invariant: INV-N8-1 (new); INV-27 (its allowlist shrinks from 28 files to 26).

## What changed

| Change | Where |
|---|---|
| The FLRL methods' descriptors, parameter properties and checks move out of the core, next to their solver, with a `FourierPlugin` that declares each method's parameters and completion units (Adam's relaxed-gradient steps count as decisions, as before) and creates `FourierOptimizer` only when a run needs one | `src/dqn_meent/flrl_methods.py` (was `optimizers/fourier_specs.py`) |
| The plug-in is registered as the lab's own `flrl` entry point, beside `mask_optimizers`; its methods keep their ids, descriptors and listing order, and, being in the lab's own package, still show as bundled in the method catalog | `pyproject.toml` |
| The core registry drops every Fourier special case (the descriptors, the properties, the completion-unit and `initial_design` exceptions, the validation hook and the `dqn_meent` import in `create()`); it keeps the problem-agnostic built-ins: `random`, `swap_search`, `coordinate`, `replay`, `evaluate_asset`, `artifact_inference`, the binary searches and the DQN | `optimizers/registry.py` |
| `optimizers/fourier_specs.py` and `optimizers/registry.py` leave the domain-names ratchet's allowlist | `tests/balsamic/test_layering.py` `NAMES_A_DOMAIN` |
| Invariant `INV-N8-1`; INV-27's known gap now counts 26 files | `docs/invariants.md` |
| The "known limits" note on the bundled FLRL methods now says where they live | `docs/optimizer-plugins.md` |

A frozen run captures the `flrl` entry point with the other optimizer plug-ins, so its worker finds the methods, and its
scientific files include `flrl_methods.py` and `flrl_optimizers.py` as before. Runs frozen before this change resume from
their own captured source and are not affected.

## Checked

- `tests/test_flrl_plugin.py` (7 tests): every method descriptor `registry.methods()` listed before the move (fixture
  `tests/fixtures/optimizer-methods-before-n8.json`, written by the old code) is listed identically and in the same order;
  the six FLRL methods come from the `flrl` entry point of the lab's own package and none is a core built-in; no module of
  `optimization_framework.optimizers` imports `dqn_meent`, and importing the registry loads none of it; two FLRL methods
  (`flrl_lsf_random`, `flrl_lsf_es`) reproduce the masks the old code proposed across a checkpoint and restore (fixture
  `tests/fixtures/flrl-runs-before-n8.json`), with the same checkpoint identity, so a run checkpointed before the move
  continues; the methods' own checks (elite count, frozen RCWA orders, no inline initial design, only the 2D deflector)
  still refuse what they refused; a frozen capture lists the `flrl` entry point and pins its solver's source.
- `tests/test_optimizer_plugins.py`: the framework imports no optimizer library or adapter, now including
  `dqn_meent.flrl_*`. `tests/balsamic/test_layering.py`: the ratchet passes with the shorter allowlist.
- The full suite (counts in the PR). `tests/test_flrl_optimizers.py` needs MEENT and torch and skips in the cloud.

## Not done

- The race's preferred FLRL methods and cost model (`execution/racing.py`) still name these ids; N5 moves them into
  MEENT's pack.
- The PPO-based methods' end-to-end checks (`tests/test_flrl_optimizers.py`) were not run here: they need MEENT and torch.
- A running service picks up the new entry point once the package is reinstalled; `scripts/start` does this through
  `uv run`. A service started from an environment that was not resynced would list the FLRL methods as unknown.

## Acceptance test

1. Update to this release and start the app with `scripts/start`.
2. Open a campaign whose task is the 2D dual-polarization deflector. Go to Hypotheses → Implementations and look at the
   Algorithms section. The six FLRL methods (`flrl_lsf_random`, `flrl_lsf_es`, `flrl_ppo`, `flrl_autograd_adam`,
   `flrl_ppo_polish`, `flrl_ppo_residual`) are there as before: under "more bundled methods that can run here", or in the
   table marked "bundled with Balsamic" and "can run" if a proposal uses one. None says "library".
3. If a proposal in that campaign used an FLRL method before the update, open it: it still names the same method and is
   still runnable. Continue or rerun one of its runs; it starts and records evaluations as before.
4. Open a campaign on any other problem (for example the knapsack or continuous benchmark). In the same Algorithms
   section, under "methods that cannot run here", each FLRL method says it runs only on
   `meent_2d_dual_polarization_deflector`.
