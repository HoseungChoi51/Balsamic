# H3 — Bring your own session

State: implemented and tested (PR pending, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

Layer: none: a missing capability, not a failure at a layer. The researcher could not deliver from their own coding agent:
a coding workspace's library entered the lab only as a commit the coding agent submitted from inside the box, through the
file bridge, and nothing outside the box could hand the host a commit, or fetch the library to start from.
Invariant: INV-22 (updated), INV-H3-1, INV-H3-2 (added).

## Checked

`tests/test_own_session.py` (9 tests; Git real, uv faked as in `test_library_install`):

- Two labs made from the ovens' charter: in one the coding agent commits the filled library on the workspace's branch in the
  box's store and submits through the bridge; in the other the researcher clones the start over HTTP, fills the same
  objective and methods, and delivers a bundle that leaves out what the host has. Both submissions have the same manifest,
  report and files (each lab's charter id aside); the researcher's is the exact commit with `source: own_session`, nothing
  answers it in the box, and the lead's notice says the researcher delivered it. Balsamic's own install of each has the same
  outcome: installed, no generated file changed, the proposal bound to its method by Balsamic, citing the install; the files
  installed are the bytes of the researcher's commit.
- A commit on top of the lab's own history (the researcher's clone of the lab) travels as a thin bundle: the host names the
  box's commit, the bundle needs it and does not carry it, and the delivery is taken; the host then names the new commit.
- No token, a wrong one, an empty one, one without `Bearer`, `Basic`, another workspace's, and the right one on another
  campaign's or a missing workspace's path: 401 on all three routes, with `WWW-Authenticate: Bearer`, and nothing is read or
  kept (no submission, no event, no store made).
- A bundle of another commit (refused, naming what it carries), a thin bundle building on a commit the host does not have
  (refused, naming it), an upload that is not a bundle, not base64, and a commit that is not a hash (422): nothing is
  captured, the host's store gets no ref, and the four refusals are on the history; the right bundle is then taken.
- The token: shown once with the CLI's path; its state says when it was made, never the token; it is in no file of the lab
  (database and journal included) and not in what agents read; its digest is kept. A new one replaces it. A stop revokes it
  ("the workspace is stopped"), no token is made while stopped, a resume does not bring it back ("stopped after it was
  made"), and a new one works.
- A paused workspace refuses a delivery ("resume it before delivering") but still lets the library be cloned; resumed, one
  past its H5 deadline is refused ("going on is a new go-ahead"); resumed with a new deadline, the delivery is taken and the
  token's last delivery is recorded.
- The start is the generated library byte for byte, under `libraries/<name>/`, as one commit by Balsamic, the same commit
  each time; a workspace that did not start from a generated library has none (409).
- In the lab's own app: a page of another origin cannot make a token (403), the lab's page can; a delivery without a token
  is 401 and leaves no issue in the campaign; the CLI's request (no `Origin`) with the token is answered.
- End to end on a real port: the CLI clones the library, the researcher commits, `submit HEAD --report` delivers it; the
  submission is that commit, the temporary ref is gone, and Balsamic's install binds the proposal.

`agent-harness/test/workspace-cli.test.mjs` (1 test more): against a fake host, `clone` leaves no remote; `submit HEAD`
posts the box's fields and a bundle of the commit that requires the start and skips a commit the researcher does not have;
a wrong token is refused with the host's words; `checkpoint` outside the box, `clone` without an address and `clone` into a
non-empty directory are refused. The six H1 tests pass unchanged (parity with the extension inside the box).

Playwright `implementations.spec.ts`: "the researcher makes a token on the card, sees it once with the commands ...": the
section says no token yet, makes one, shows the commands with the token, the workspace's address and the lab's CLI path;
after a reload it says a token is active and shows no token anywhere on the page; a stopped workspace offers none; a
delivery from the researcher's session reads "from your own session". All 15 Implementations tests pass; `npx tsc -b` is
clean.

The development, install, binding, CLI, layering, invariant and readiness suites, and the full Python suite, pass (counts in
the PR). Docker is not available in the cloud container: the Docker driver's own paths are not run here (the tests use a
fake driver with real Git stores).

## Not done

- Continuing from the coding agent's own commits: the start is the generated library, and a commit of the researcher's
  own clone of the lab builds on the lab's history; the box's branch itself is not served (its store is the coding agent's
  to write, and the host never runs it as a repository).
- A workspace that did not start from a generated library (a campaign without a charter) has no start to clone; the
  researcher delivers from a repository of their own that holds `libraries/<name>/`.
- The researcher's delivery report is theirs to write (the card says so; `check` gives the test counts); nothing drafts it.
  The start holds the library only, not the box's brief (`.campaign/assignment.md`): the ticket's `TASK.md` and `AGENTS.md`
  for any harness are H4's.
- Validation outside the box (H6) is not merged yet: when it is, it reads the commit through `Installer.files()`, which
  already takes the researcher's commit from the host's store.
- The token is a bearer secret over the lab's own HTTP (plain HTTP on `127.0.0.1` by default); reaching the lab from
  another machine is the deployment's matter (a tunnel, `GRATING_DEVELOPMENT_PUBLIC_URL`), as for the IDE.
- Tokens do not expire on their own; they end when replaced or when the workspace stops.

## Acceptance test

Before: restart the lab with coding workspaces on, and have Git and Node 22 on your machine (the commands below run the
CLI from the lab's checkout, so nothing is installed).

1. In a campaign made from a confirmed charter whose evaluator is declared, give the team the go-ahead to implement a
   proposal in a coding workspace. On the Proposals page, open **Implementations** and find its card under **Coding
   workspaces**.
2. Open **Deliver from your own coding agent** on the card. It says "No token yet." Press **Make a token**. Expected: a
   block of commands appears with your token in it, and the text says it is shown only this once. Copy the block.
3. Reload the page and open the section again. Expected: "A token made … opens this workspace. It is not shown again"; the
   token is nowhere on the page.
4. In a terminal on your machine (or ask your own coding agent to do it), run the copied commands up to `cd`. Expected:
   `clone` prints "Cloned libraries/<problem id> (commit …) into <problem id>", and the folder holds the generated library
   (`charter.json`, the package with `data.py`, `objective.py`, `methods.py`, `adapter.py`, and `tests/`).
5. With your own coding agent, write the objective and one method there (`objective.py`, and `methods.py` under a METHODS
   key of your choosing), commit, write `report.json` (the delivery report, as the coding agent writes one: a verdict, that
   METHODS key as the method's id with the proposal's id, `hypothesis_…`, from the proposal's link on the card, and the test
   counts the `check` command prints), and run the `submit HEAD --report report.json` command. Expected: "Submitted
   development_submission_… Independent validation has not been run yet."
6. Back on the card, within a minute or two: the result reads "Delivered commit … from your own session" with your verdict;
   Balsamic installs it by itself (the install box says installed, by Balsamic) and binds the proposal to your method; the
   History lists the delivery "from your own session". The lead is told you delivered it.
7. Run the `submit` command again with a wrong `BALSAMIC_WORKSPACE_TOKEN`. Expected: "401: The token does not open this
   workspace". Pause the workspace and submit again: refused, "The workspace is paused: resume it before delivering to it".
8. Stop the workspace. Expected: the section says the workspace is stopped and offers no token, and the old token is
   refused ("the workspace is stopped"). After a resume the old token still does not work; a new one does.
