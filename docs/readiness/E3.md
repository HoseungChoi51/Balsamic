# E3 — The charter recognizes an installed declared problem

State: implemented and tested (PR pending, 2026-10-27); not checked live.

## What was wrong

A charter declares a problem (an evaluator still to be built) under an id. Once the coding agent's library providing that
problem was installed, the charter got the blocking finding `evaluator.declared_id` ("a declared problem needs a new
identifier, or use the installed one"), so the very library written for the charter blocked it. Nothing compared what the
library computes with what the charter says, and `compile_setups()` always emitted the declared setup with its own
`evaluator_manifest`.

## What changed

| Change | Where |
|---|---|
| `compare_provided(manifest, instance)`: a pure function listing each difference between the declared problem and the library's resolved problem: candidate schema (representation, dimensions, bounds, values, constraint names), primary objective (name, direction, units, with "", "1" and "dimensionless" the same), the charter's metrics the library does not report, and the configuration field names. Each difference says what the charter says and what the library computes. F3's contract test can call it | `problem_charter/charter.py` |
| When a declared `problem_id` is installed, the charter's values are resolved with the library and compared. No difference: an informational finding `evaluator.provided` ("provided by <distribution> <version>"). Any difference, or a library that refuses the charter's values: a blocking, unwaivable `evaluator.provided_mismatch` listing each one, with the configuration field names when the library refuses them. `evaluator.declared_id` is gone | `problem_charter/charter.py` `evaluator_findings()`, `provided_finding()` |
| `compile_setups()` emits an installed setup (`problem_id`, configuration, fidelity) for a provided problem, and refuses a declared id that is installed but could not be compared | `problem_charter/charter.py` |
| `describe()` returns `evaluator`: `kind` is `installed`, `declared`, or `provided` (with `provided_by`) | `problem_charter/charter.py` |
| A discovered registry records the distribution and version of each problem's entry point, `ProblemRegistry.source(name)`; without one, the finding names the problem's own version | `evaluation/registry.py` |
| The Charter page shows informational findings as a line under the summary ("provided by a library"), not among the warnings; a mismatch is a check like any other | `frontend/src/note/CharterPanel.tsx` |
| New invariant row INV-E3-1 | `docs/invariants.md` |

## Checked

- `tests/test_problem_charter.py`: a matching library gives `evaluator.provided` naming its distribution, no blocking
  finding, and (installed in the lab's registry) an installed setup whose task resolves; a library that minimizes what the
  charter maximizes, with another size and no constraints, is blocking with exactly those differences listed and is not
  waivable, and compiling is refused; units, metrics, representation and values are each a difference while "1" and
  "dimensionless" are not; a library without one of the charter's configuration fields is a difference in the field names;
  not installed, the declared path is unchanged (`evaluator_manifest`, kind `declared`); an installed charter's kind is
  `installed`; every installed problem names its distribution.
- `frontend/tests/charter.spec.ts`: the provided note shows above the checks and not among the warnings; a mismatch shows
  as a check.
- Full suite (see the PR for the counts).

## Not done

- Existing tasks keep their declared problem: adopting the library's problem into a campaign's tasks is E4.
- The comparison uses the charter's own values; instances that change the configuration are compiled with the installed
  problem without a comparison of their own.
- Not checked live: no installed library provides a declared charter on the dev stack yet (E2 lets a problem library be
  installed).

## Acceptance test

Needs a problem library installed for a declared charter, which E2 makes possible; until then this is checked by the
tests above.

1. Start the app and open a campaign whose charter declares a problem to be built (for example baking order, whose
   evaluator is "to be built"), and have the coding agent write and install the library that provides it, under the same
   problem id.
2. Open the Charter page (the problem note's Charter tab). Under the summary, a line marked "provided by a library" should
   say the problem is provided by the library's package and version. It should not appear among the warnings, and no
   blocking check should say the id is already installed.
3. Confirm the charter. It should confirm without asking for an evaluator to be commissioned, and the campaign's task
   should name the installed problem.
4. In a copy of the charter, change the objective's direction (minimize to maximize) and save. A blocking check marked
   "library computes another problem" should list "objective direction: the charter says maximize, the library computes
   minimize", it should offer no Waive, and Confirm should stay disabled until the direction is changed back.
