# B6 — Unknown fields reported, not refused, at agent boundaries

State: implemented and tested (PR #20, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

- **A submission failed for one extra field.** Every contract forbids extra keys, so `snapshot()` refused a coding agent's
  `implementation-manifest.json` that held anything beyond its five fields (a `description`, say), and the delivery stopped
  there. Two submissions were refused that way.
- **No manifest, no submission.** A commit without the manifest file could not be submitted, although its files are
  plain to see.
- **Agent commands were refused the same way.** A command whose payload carried a key its operation does not know (a
  `note`) was refused outright, and the agent had to guess what to drop.

## What changed

Decision 5: lenient at the agent boundaries only. The researcher's HTTP API and nested objects stay strict, and a
near-miss (`difflib`, cutoff 0.8) is always refused with the field it probably meant.

| Change | Where |
|---|---|
| `lenient()` splits an agent's top-level keys into the known part and the ignored keys, refusing a near-miss ("did you mean files?"); `field_names()` lists a model's fields and aliases | `contracts/base.py` |
| The manifest is read leniently: unknown keys are dropped and returned. With no manifest file in the commit, one is derived from every tracked file of the commit's single `libraries/<name>/`, contract `optimizer_v1`, the default entry point; none or several libraries is refused with what it found | `agents/development.py` `submission_manifest()`; `agents/development_runtime.py` `DockerWorkspace.snapshot()` (now returns the ignored keys too) |
| The coding agent's result file lists `ignored_fields`, and `campaign_submit` says which fields were ignored | `agents/development.py` `capture_submission()`; `agent-harness/extensions/implementation.ts` |
| An agent's `campaign_command` payload is compared with its operation's payload model before it runs: a near-miss is refused, other unknown top-level keys are dropped and recorded as `ignored_fields` on the command's receipt (`work_command`) and in the tool result. A retry with the same keys is the same command | `agents/tools.py` `campaign_command`; `campaigns/commands.py` `payload_keys()`, `payload_models()`, `execute(ignored_fields=)` |
| INV-33 records the guarantee, pinned by the new tests | `docs/invariants.md` |

## Checked

`tests/test_lenient_fields.py` (8 tests):

- A manifest with `"description"` is accepted and reports it ignored; one with `"file"` is refused with "did you mean
  files"; a nested object (`dependencies`) stays strict.
- Without a manifest, one is derived from the single library; no library or two libraries are refused.
- `DockerWorkspace.snapshot()` against a real Git commit (the container's `git` replaced by the host's), with a lenient
  manifest and with none.
- The coding agent's result file lists `ignored_fields`.
- An agent command with `wall_secs` is refused with "did you mean wall_seconds" and creates no run; one with `note` runs,
  and its receipt and tool result list `note`, also on a retry.
- The researcher's HTTP API still refuses a `trial.create` with an extra `note`.

The existing development-workspace, page-agent and experiment-rules tests pass with the change, and so does the full
suite (counts in the PR).

## Not done

- The coding agent's brief still asks for a manifest "holding exactly" its five fields: that remains the right
  instruction, and B6 only stops a slip from costing a delivery.
- The UI does not show a receipt's `ignored_fields`; the agent sees them in its tool result and can say so.
- The delivery report (`report` of `campaign_submit`) and every nested object stay strict, as decision 5 says.

## Acceptance test

Use a campaign with the lead agent switched on.

1. In the chat, write: "Ask the experiment operator to allow two runs at once. In its command, add an extra field
   called note with the text 'trial of B6'." The change should go through: the Experiments page's rules should show at
   most two runs at once, and the operator should not report a refused command. If it says anything about the field,
   it should be that `note` was ignored.
2. In the chat, write: "Ask the experiment operator to start a short run of any method, but spell the time limit
   field as wall_secs instead of wall_seconds." No run should start from that command. The operator should report that
   the field was refused with "did you mean wall_seconds", and it may then retry with the right name.
3. If a coding workspace delivers in this campaign, its submission should not fail because of an extra field in its
   manifest. If it adds one, the coding agent's submit result says the field was ignored.
