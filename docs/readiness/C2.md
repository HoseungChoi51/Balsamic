# C2 — Built-in methods for permutations

State: implemented and tested (PR #24, 2026-10-27); not checked live.

## What was wrong

C1 let a problem's decision be an order, but the only built-in method that could search one was `random`. Nothing in the
lab improved an order step by step, and the two reference methods, `replay` (evaluate listed candidates) and
`evaluate_asset` (evaluate a declared solution), still refused orders, so a recorded or hand-written order could not be
evaluated.

## What changed

| Change | Where |
|---|---|
| New built-in `swap_search` ("Swap search"), for permutations only. It starts from a random order and tries the current order's neighbours (every swap of two items, and every move of one item to another position at least two places away) in a seeded random order; the first neighbour that improves becomes the current order. After `restarts_after` evaluations without improving the current order (by default a whole neighbourhood, so at a local optimum) it restarts from a new random order. Its checkpoint is plain JSON, including the generator's state | `optimizers/swap_search.py`, `optimizers/registry.py` |
| `replay` and `evaluate_asset` list `permutation`: each listed order, or the declared solution, is checked as an order and evaluated once | `optimizers/registry.py` |

## Checked

- `tests/test_swap_search.py` (7 tests): the neighbourhood of 8 items has its 28 swaps and 42 insertions, all distinct;
  on an 8-bake total-tardiness instance swap search reaches the optimum found by enumerating all 40,320 orders within
  300 evaluations for seeds 0–3 (at evaluations 51, 55, 144 and 124), proposes only orders, and repeats itself for a seed;
  a lower `restarts_after` restarts more often; `restarts_after` must be a positive integer and `initial_design` is
  refused; a binary problem is told it requires permutation candidates; `conformance.check()` passes; a checkpoint taken
  mid-search continues the same search, and one whose current order is not an order is refused; `replay` evaluates each
  listed order and refuses a repeat; `evaluate_asset` evaluates a declared order once and refuses a short one.
- `tests/test_permutations.py` (C1) still passes.

## Not done

- No start order for swap search: like every non-binary built-in, it refuses an inline `initial_design`.
- Not checked live on the dev stack.

## Acceptance test

1. Start the app and open a campaign whose problem is an order, such as baking order (the order of 8 bakes to minimize
   total tardiness) with its charter written as an order (C1's acceptance test).
2. Where the task's methods are listed, "Swap search" should be available, alongside "Uniform random", "Evaluate listed
   candidates" and "Evaluate a reference solution". On a campaign whose problem is not an order, Swap search should be
   unavailable with the reason "requires permutation candidates".
3. Run Swap search and Uniform random on the task for the same number of evaluations (a few hundred). Every evaluated
   design should be an order of 0 to 7 with each number once. Swap search's best total tardiness should typically be at
   least as good as random's, and its progress should improve in steps, with an occasional restart showing as a worse
   evaluation after a flat stretch.
4. Ask the lead to evaluate two or three specific orders you write down (it uses "Evaluate listed candidates"). Each order
   should be evaluated once, in the order you gave, and the recorded tardiness should match what you would compute by
   hand. An order with a repeated bake should be refused before anything runs.
