# H7 — Commissions run as headless boxes

State: implemented and tested (PR pending, 2026-10-27; `main` with H1–H6 merged); J4 run headless and the acceptance test on a
live lab are Hoseung's.

## What was wrong

Layer: evidence. A commission's code entered the lab on a second route, checked by what that route's own roles said rather
than by validation of a library outside the box.
Invariant: INV-H7-1, INV-H7-2, INV-H7-3, INV-H7-4 (added); INV-25, INV-29 (updated).

- **Three routes built code.** `implementation.commission` and `evaluator.commission` went to the implementation service: a
  builder, a test designer and a validator (Pi grant roles) with restricted file tools (256 KiB a file) and a sandboxed Python
  runner of at most 30 s a call, writing a package for the service's own contract; the coding workspace built a library on
  another. Two logs (the job's trace, imported, and the workspace's timeline), two cost paths, two contracts.
- **The protected tests were the service's.** The test designer designed them inside the job; nothing of it reached the library
  route, which H6 validates outside the box.
- **Nothing ran a commission headless.** H2 gave the box a headless mode; nothing opened a box for work nobody watches.

## Not done

- **J4 run headless is Hoseung's**, with the acceptance test below: Docker is not available here.
- **The bridge's own commission path still reaches the service**: `ImplementationBridge.commission()`/`reserve_commission()`, which
  the HTTP route `POST /api/hypotheses/{id}/implementation_jobs` and a workspace's `implementation_workspace_validate` use. H8 has
  it call H7 and retires the job's agent loop, the grant roles and `implementation_workspace_validate` (the third route).
- **Service jobs remain** for a commission while coding workspaces are off, for a package import, and for an evaluator for a task
  no charter declares (nothing has such a task adopt an installed problem: `campaign.adopt_problem` needs a charter). H8 decides
  each.
- The specification's behaviour, mechanism and diagnostic checks are not run as protected tests: they ran against the service's
  ask/tell runtime and its binary fixtures, and the builder saw them there too. They are in `TASK.md`'s frozen specification for
  the coding agent's tests; the commissioner writes what must hold as a protected pytest file.
- `max_calls` and `api_budget_usd` are recorded on the box, not enforced: the box's model use is counted on it as any box's, and
  nothing reserves those dollars against the campaign's model cap as a job did.
- `implementation.control` (cancel or resume a job) does not reach a box: the researcher pauses, resumes or stops it on its card.
- A commission's box is not offered to anyone to attach; the IDE still opens it, and the researcher's messages reach it as any
  workspace's.

## Acceptance test

Before: restart the lab with coding workspaces on (`development_enabled` in the launcher file), as for any workspace change. The
image need not be rebuilt: the box's tools are mounted from the checkout.

1. In a campaign made from a confirmed charter whose evaluator is declared (the ovens or the baking order), with the lead agent
   on, open **Proposals → Implementations** and write to the implementation lead: "Commission an implementation of <a proposal>
   (implementation.commission), with a protected test that no method returns a candidate the charter does not allow. Do not open
   a workspace yourself." Approve the Screen mandate card it sends.
2. A new card appears under **Coding workspaces** with a **Commission** row: "an implementation job of N min: <the
   specification's name> · protected tests outside the box: test_….py". Nobody attaches to it: its **History** opens with
   "Commissioned by the implementation lead under your go-ahead" and fills with "Worked …" entries by itself.
3. Open its editor. `TASK.md` has a section "The commission" with the mechanism and each acceptance criterion. Search the
   workspace for a phrase of the protected test: it is not there.
4. When it delivers, the card shows the delivery, then the install **checking outside the box**, then **installed**, with the
   protected test listed by name and outcome; the proposal is bound to its method by Balsamic. The implementation lead reports the
   result to you.
5. The line above the chat shows the mandate's worker time less the commission's minutes, once, however long the box ran; no
   coding workspace of the mandate is used.
6. Ask the implementation lead to commission the campaign's evaluator (evaluator.commission) with one fixture you give (a
   candidate and the objective it must give). A card for "the evaluator of task …" appears with no proposal; once it delivers and
   installs, the campaign's tasks take the problem the library provides. Asked with a wrong fixture value, the install fails
   outside the box and names the fixture test, not its numbers.
7. Turn coding workspaces off and restart: a commission is an implementation service job again, as before this part.
