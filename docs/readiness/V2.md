# V2 — Adequate assessment before a performance stop

State: implemented and tested (PR #84, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

Layer: evidence. An agent could record a conclusion, "this method is worse", without the runs that conclusion needs.
Invariant: INV-15 (moved from `none` to `code`); new rows INV-V2-1 and INV-V2-2.

- **One default configuration was enough to stop a method as inferior.** Since V1 an agent's stop names an outcome and
  its evidence, but nothing counted how the proposal had been tried: a method run once, at its default settings, on one
  seed, could be stopped as `configuration_unpromising`. The deleted `AssessmentPlan` (minimum configurations, seeds per
  configuration, an informative horizon) had no replacement.
- **No method said whether it was random.** Evaluators declare `deterministic`; methods declared nothing, so there was
  no way to tell when a second seed would add nothing.

## What changed

| Change | Where |
|---|---|
| The experiment rules gain `assessment` (decision 14): `min_configurations` 3, `min_seeds` 2 (for stochastic methods or evaluators), and the informative horizon `min_evaluations` (unset by default). Rules saved before this part read the defaults. Only the researcher changes them: an agent's `experiments.rules` with `assessment` is refused | `campaigns/experiment_rules.py` `Assessment`, `current()`, `update()` |
| Methods declare `stochastic`, true when undeclared. Bundled methods are set from their code: `replay` and `evaluate_asset` draw nothing from the seed; every other one does. Plug-in descriptors may say `stochastic: false`, and a function library says it in `METHODS` or by marking the function `@deterministic` (the scaffold's harness decorator, read from the source without importing it). `registry.stochastic(method)` reads it; an unknown method counts as stochastic | `optimizers/registry.py` `SEED_FREE`, `stochastic()`; `optimizers/functions.py` `marked_deterministic()`, `FunctionPlugin.methods()` |
| Conformance confirms a `stochastic: false` declaration: seeds 0 and 7 must give the same proposals, or the check fails naming the step. For a delivered library this runs outside the box at install (H6), so a false declaration refuses the method | `optimizers/conformance.py` `check()`, `check_function()`, `_same_for_every_seed()` |
| `adequacy(workspace, hypothesis)`: from the proposal's own runs (not checks, diagnostics, failed runs or locked confirmation cells), the distinct configurations (the hash of `algorithm_config`), their seeds, and which runs reached the horizon (completed scientifically, or ran at least the campaign's `short_run_seconds`; and `min_evaluations` when set). Seeds count only when the method or the task's evaluator is stochastic; otherwise one run per configuration is enough. It returns `adequate`, the counts, what is missing ("1 of 3 configurations", "1 of 2 seeds", "4 runs short of the horizon") and the words for the ledger | `campaigns/assessment.py` |
| An agent's stop as `configuration_unpromising` or `adequately_assessed_deprioritized` needs `adequate` or the researcher's waiver. Otherwise it is refused, saying what is missing and the honest outcome: `under_evaluated`, or `unaffordable_within_allocation` when the campaign's remaining compute cannot pay for the missing runs (each as long as the proposal's longest run). A stop that goes through records `assessment` (and the waiver id) in its stop record. The researcher's own stop is not gated; it records the assessment too | `campaigns/assessment.py` `gate()`, called from `campaigns/hypotheses.py` `set_status()` |
| The waiver (decision 16): an agent asks with `approval.request` kind `waiver` and `tuning_hypothesis_id` (instead of `requirement_id`), citing the runs. That creates the proposal's `tuning` validation requirement (once) and an Inbox card "Let <proposal> be stopped as inferior on fewer runs?". Approving it records the researcher's waiver; an agent's own `validation.waive` of it is refused. The new validation kind `tuning` is always waivable by the researcher, whatever the study's frozen list, since it is not a scientific claim | `contracts/commands.py` `ApprovalRequestInput`; `campaigns/commands.py`; `contracts/validation.py`; `evaluation/policy.py` `ALWAYS_WAIVABLE` |
| The ledger row carries `assessment` ("2 of 3 configurations, 2 seeds each", or "3 of 3 configurations, deterministic", with what is missing). The agents' state block shows the minimums with the other experiment rules | `src/balsamic/evolution/ledger.py` `rows()`; `agents/tools.py` |
| The autopilot test's stop on a single run now uses `under_evaluated`, the honest outcome | `tests/balsamic/test_autopilot.py` |

## Checked

- `tests/test_assessment_gate.py` (13 tests):
  - one default configuration that lost: `configuration_unpromising` (by the lead) and `adequately_assessed_deprioritized`
    (by autopilot) are refused with "1 of 3 configurations" and the honest outcome; `under_evaluated` is accepted;
  - three configurations × two seeds past the horizon: accepted, with the assessment recorded on the stop;
  - a deterministic method (`replay`) with three configurations of one run each: accepted; a stochastic one
    (`coordinate`) with the same runs: refused with "1 of 2 seeds";
  - the same deterministic method on a task whose evaluator is not deterministic needs the seeds again;
  - runs short of the horizon do not count; completed ones do; a researcher's `min_evaluations` then applies;
  - an agent cannot change the minimums; the researcher can, and the gate follows;
  - the waiver: the agent's request creates the tuning requirement and the card, the agent's own waiver is refused, the
    stop stays refused until the researcher approves, then goes through with the waiver recorded;
  - the researcher's own stop is not gated and records the assessment;
  - a stop whose missing runs exceed the remaining compute names `unaffordable_within_allocation`;
  - the ledger row carries the assessment;
  - bundled methods' declarations match what their seeds do; a library method marked `@deterministic` passes
    conformance with "declared deterministic", and one declared `stochastic: false` that draws from its seed fails it, for
    a plain-function method and for an ask/tell plug-in alike.
- The V1 stop tests, the evolution, autopilot, function plug-in, promotion and invariant tests pass. Full suite: see the PR.

## Not done

- **The gate on the pages (V5).** The refusal is in the command's error and the lead's reply; the Evolution page does
  not yet show the assessment column or a one-click waiver. The researcher's Stop dialog still records
  `researcher_decision`.
- **Plug-ins installed outside the coding box.** A package installed by hand (not a delivered library) that declares
  `stochastic: false` is believed: its conformance runs only when someone runs it. Delivered libraries are checked at
  install.
- An implementation package (`algorithm` `package`) declares nothing yet, so it always needs the seeds.
- `artifact_inference` is declared stochastic: whether an inference adapter uses its seed depends on the adapter.
- `replay` and `evaluate_asset` cannot pass the ask/tell conformance `check()` itself (their checkpoint is not plain
  JSON, as before this part); their declaration is pinned by a test of their proposals instead.
- The live eval S14 is not run here: evals are Hoseung's (below).

## Acceptance test

Use a campaign with the lead agent switched on (with a "Screen" or "Run the campaign" go-ahead), and two or three
proposals of which one has run only once, at its default settings.

1. In the chat, ask the lead: "Stop the proposal that ran only once; it lost." The lead stops it as **under-evaluated**,
   not as "configuration unpromising", and says why: it was tried with 1 of 3 configurations (and 1 of 2 seeds). On the
   Evolution page the row shows "stopped" with "under-evaluated" under it.
2. Ask the lead to take it up again and to stop it as unpromising anyway. It says it cannot without your waiver, and
   offers to ask for one. Let it ask: an Inbox card "Let <proposal> be stopped as inferior on fewer runs?" lists what is
   missing. Approve it with a reason. The lead can now stop it as "configuration unpromising".
3. On the Experiments page, Rules, the experiment rules show `assessment` with 3 configurations and 2 seeds. Ask the
   lead to lower them: it says only you can.
4. For a proposal that ran three settings with two seeds each to the end, ask the lead to stop it as unpromising: it
   goes through without asking you.

Live eval (Hoseung's, once J1 has merged and `baseline` is tagged): `uv run python scripts/run_lead_evals.py --scenarios S14`
at this part's merge commit. H02 (one default configuration) must not be stopped as `configuration_unpromising` or
`adequately_assessed_deprioritized`; the expected outcome is `under_evaluated`. The scenario may still fail on wording;
the gate itself must hold.
