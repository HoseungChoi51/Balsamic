# H4 — The work ticket

State: implemented and tested (PR pending, 2026-10-27; `main` with H5 merged in); the live checks (the acceptance test and
J4 on the ticket route) are Hoseung's.

## What was wrong

Layer: prompt. What the coding agent was asked to do, and how the implementation lead followed it, lived in prose: a brief
of generic instructions and the proposals' JSON, and chat messages relayed into the box.
Invariant: INV-H4-1, INV-H4-2, INV-H4-3 (added).

- **The coder got a JSON dump.** `.campaign/assignment.md` was the proposals' full records and `DEVELOPMENT_INSTRUCTIONS`;
  what to build, how to test it and how to deliver were Pi-only prose, and no other harness had a file it reads by itself.
- **Nothing said when the work was done.** No record held the acceptance tests, so nothing could refuse a workspace opened
  with none, and there was nowhere on the host for tests the coder must not see.
- **The budget and the walls were not stated to the coder.** The go-ahead, the mandate's model envelope, the deadline,
  the limits and the network (H5) were on records the coder could not read.
- **The implementation lead relayed chat instead of reviewing work.** It steered with `implementation_workspace_message`
  and read checkpoints; `implementation_workspace_inspect` showed state, questions and submissions but no diff.

## Checked

`tests/test_development_ticket.py` (7 tests):

- `prepare()` of the Docker driver (its worktree made beforehand; no Docker here) writes the four files for a ticket with
  the generated library, the implementation lead's test and its protected test: `AGENTS.md` and `CLAUDE.md` are the ticket's
  house rules, `TASK.md` lists the generated and the lead's tests and names the protected one, `spec.json` is the ticket
  without the tests' source. The protected test's source is in its host record and nowhere under the box's directories.
  A second `prepare()` keeps an edited `TASK.md` and an edited lead's test, and writes back a removed `CLAUDE.md`. A sync
  through the workspace's driver writes the same four files, and the session brief names `TASK.md` and `AGENTS.md`.
- The house rules hold what to build, how to run the tests, how to submit and what not to touch; what moved there left
  `DEVELOPMENT_INSTRUCTIONS`, now shorter than at F4 in words and characters.
- A ticket without acceptance tests is refused by `check_self_contained()`, and an agent's workspace with one is refused
  before anything is recorded or charged. A ticket naming a record the coder cannot read is refused; given as evidence, the
  record is readable.
- A charter campaign's ticket has the generated tests without the lead naming any; a lead's test that would overwrite a
  generated file, or sit in `.balsamic/`, is refused; the researcher's own workspace is opened on a ticket and not refused.
- Under a Screen mandate approved with a model envelope, a deadline and `github.com`, the ticket carries the consent's
  worker time, the envelope, the CPU allowance, the wall time and the request's deadline, the limits, and the approved
  host, which the workspace reaches although its request named none; `TASK.md` states each.
- `implementation_workspace_inspect`, called as the implementation lead's tool, returns the diff summary of a real commit
  read from the workspace's Git store: five files, the harness's one added line, the new module, the lead's test changed;
  `harness.py` as the generated file touched (not the objective or the methods), the lead's test as the acceptance test
  touched, no fixed file. The delivery's notice to the implementation lead names the change.
- The diff compares by hash a generated file whose bytes are not at hand, and counts no lines for a binary file.

## Not done

- **J4 on the ticket route is not recorded.** It needs Docker, the workspace image and a model provider: Hoseung's (below).
- **H6 is not merged.** Protected tests are stored where H6's draft reads them (`development_protected_test`, the same id),
  but nothing runs them yet; `review.host_validation` and `refused_methods` stay None until H6 records them on the install.
- **The Implementations page shows neither the ticket nor the diff.** The researcher sees the ticket in the workspace's
  editor; the diff reaches the implementation lead (its review and the delivery's notice), not the page.
- **The ticket is fixed when the workspace opens.** A change of plan goes to the coder as a message; the ticket is not
  revised, and `check_self_contained()` does not see such a message.
- The proposals reach the coder as their title, mechanism and `METHODS` key, as the roadmap names them; their other fields
  (rationale, assumptions, risks, configuration) are no longer in its brief. A lead that needs one in the work states it in
  the objective or a test.
- `implementation_workspace_message` is not restricted in code to answers: an agent may still send one without a
  `question_id`; the tool and the procedure say what it is for.
- A lead's test given with content at a path the repository already has is not written (the worktree's file stands); the
  diff then compares the delivery with the lead's content.
- Pi may read both `AGENTS.md` and `CLAUDE.md`; they are the same text.

## Acceptance test

Before: rebuild the coding-workspace image and restart the lab with coding workspaces on, as for any workspace change.

1. Create a campaign from a confirmed charter whose evaluator is declared, and in the main thread ask the lead to implement
   two of its proposals in one coding workspace, with one extra check the library must pass that the coding agent is not to
   see (say, "the methods must never return a candidate above the heater limit; keep that test from the coding agent").
   Approve the one go-ahead it asks for.
2. On Proposals → Implementations, open the workspace's editor. Expected at the top of the repository: `TASK.md` naming both
   proposals with their `METHODS` keys, the charter revision, the acceptance tests (the generated library's tests, and any
   the implementation lead added), the protected test by name only, the go-ahead's worker time, the deadline, the limits and
   the hosts it may reach; `AGENTS.md` and `CLAUDE.md` with the same house rules (what to build, how to run the tests, how to
   submit, what not to touch); `.balsamic/spec.json`. Search the workspace for the hidden check's text: it should not be
   there.
3. Open `.campaign/assignment.md`: it should be short, point to `TASK.md` and `AGENTS.md`, and hold no block of JSON.
4. While the coding agent works, the thread should not get a message per step. If it asks a question, the implementation
   lead answers it; nobody relays its progress.
5. When it delivers, the implementation lead's message (on the Implementations page, or the lead's in the thread) should say
   how many files and lines changed against the generated library and name any generated file it changed besides the
   objective and the methods.
6. Ask the implementation lead, on its page, to open a coding workspace for a campaign made without a charter, without
   saying what it must pass. It should either name a test for the library to pass (such as its `tests/test_contract.py`) or
   come back saying it needs one; a workspace without any is refused.

Live eval (J4 on the ticket route), on the machine with Docker, the workspace image and the harness built, at the commit
that merges this part: `uv run python scripts/run_coding_evals.py --scenarios C1 --compare evals/coding/baselines/<the Phase 2
baseline>.json` (or `--record-baseline` if no Phase 2 baseline was committed). Expected: the C1 row beside its baseline,
`metrics.ticket` showing the ticket route (one acceptance test, the library's contract test), and the time to the
submission, the turns and the messages relayed to the coding agent compared with the baseline. Commit the result as
`evals/coding/baselines/<commit>.json`.
