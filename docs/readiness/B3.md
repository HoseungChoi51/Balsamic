# B3 — The implementation allocation becomes an optional ceiling

State: implemented and tested (PR #22, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

- **Every commission needed a second approval.** `implementations/bridge.py` refused a commission or a revalidation when
  committed plus requested seconds exceeded `implementation_compute_budget_seconds`, which defaults to 0. So before any
  build the lead asked the researcher to raise the implementation allocation, on top of the compute go-ahead the bus guard
  already requires for an agent's `implementation.commission`, `evaluator.commission` and `implementation.revalidate`.
  Baking order needed two raises.
- **The texts sent agents to the allocation.** The submission notice, the validation tool, the campaign manager's
  instructions and the implementation-supervision procedure all said to work "within the implementation allocation".

## What changed

| Change | Where |
|---|---|
| The allocation is the researcher's optional ceiling: both checks apply only when it is positive; 0, the default, sets none. The refusal names the ceiling | `implementations/bridge.py` `over_ceiling()`, used by `commission()` and `reserve_revalidation()` |
| The researcher can remove the ceiling (set 0) even with implementation time committed; lowering a positive one below what is committed is still refused | `execution/service.py` `update_campaign()` |
| An agent's `approval.request` of kind `campaign_limits` that raises or removes the ceiling is refused: "Ask for a compute go-ahead (kind compute) instead; the implementation allocation is only an optional ceiling". Asking to lower a positive ceiling is still allowed | `campaigns/commands.py` `approval.request` |
| The texts say "under the compute go-ahead" instead of "within the implementation allocation" (no added prompt words) | `agents/development.py` `capture_submission()`, `agents/tools.py` `implementation_workspace_validate`, `llm/adapter.py`, `src/balsamic/procedures/implementation-supervision/SKILL.md` |
| The docs say the same | `docs/implementation-service.md` (Commission, step 1), `docs/resource-allocation.md` |
| New register row INV-30, next to INV-02 | `docs/invariants.md` |

## Checked

- `tests/test_implementation_ceiling.py`: with the ceiling at 0, an agent's commission is refused by the bus guard until the
  researcher approves a compute go-ahead for its proposal, then goes through without any raise; a positive ceiling still
  caps (the refusal names it), cannot be lowered below what is committed, and can be removed with 0; an agent's request to
  raise or remove it is refused with the redirect and creates no card, while a request to lower it still makes one.
- The existing implementation, revalidation, evaluator and compute-consent tests pass unchanged, and the prompt-size
  ratchet (`tests/test_harness_contract.py`) holds.

## Not done

- The charter still shows the field as "Implementation allocation" in approval cards (`campaigns/decision_presentation.py`);
  only its meaning changed. B7 rewrites the lead's instructions and the supervision procedure as a whole.
- The app has no field for the ceiling; the researcher sets it through `campaign.update`, as before.
- The API dollar cap for implementation jobs is unchanged: it stays shared with the agents' model spending.

## Acceptance test

Use a new campaign, created without touching the implementation allocation (it stays 0), with the lead agent switched on
and at least one proposal that needs code.

1. In the chat, ask the lead to have the proposal implemented by the implementation service. Expect one approval card, a
   compute go-ahead ("Start this work now?"). There should be no card asking to change the campaign's limits or raise the
   implementation allocation.
2. Approve it with "Start now". The implementation job should start (a "Commissioned … with …s of implementation time"
   message in the chat), with no further approval.
3. In the chat, write: "Ask me to raise the implementation allocation to 1 hour." No card to change the limits should
   appear; the lead should say that it has to ask for a compute go-ahead instead.
4. Optional: in an older campaign whose implementation allocation was already raised, ask for a job longer than what is
   left of it. After the compute go-ahead, the job should still be refused, and the message should name the allocation
   ("the implementation ceiling the researcher set"). The app has no field to set the ceiling; it stays a limit of the
   researcher's API (`campaign.update`).
