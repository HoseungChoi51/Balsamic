# B5 — Approved runs start by themselves

State: implemented and tested (PR pending, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

Layer: mandate. Nothing acted on an approved plan's runs: the lead had to notice the install, bind, hand the runs to the
operator, and the operator launched them, so approved runs waited on agent turns.
Invariant: INV-B5-1 (new), INV-B4-1 (updated).

- **Approved runs waited for an agent.** A compute go-ahead recorded the plan's runs (B2), but `grant()`'s caller said "the
  requester starts the work". After a coding workspace delivered and Balsamic installed and bound its methods (B4), nothing
  started the runs the researcher had already approved.
- **Nothing woke the lead when an approved plan was done.** The lead had to keep checking until every run had ended before
  writing the comparison.

## What changed

| Change | Where |
|---|---|
| `launch_ready(workspace, campaign_id)`: for each consent in force with `runs`, each planned run whose proposal can now run (bound to an installed method that fits the task, not a default method, concept review not blocking, evaluator ready) gets one trial per planned seed not yet run since the go-ahead, through the bus as `balsamic`, with the planned task, seed, wall time, evaluations (`max_steps`) and device. A planned task that was superseded runs on its successor (`superseded_by_task_id`, for E4) | `campaigns/plan_runs.py` (new) |
| It runs after `install_delivered()` in each workspace sync, and after the automatic binding in `after_install()`, so the order is bind, then launch. The install record lists the runs it started (`launched`) and the notice names them | `agents/development.py` `sync()`; `agents/library_install.py` `after_install()`, `bound_text()` |
| `balsamic` may run `trial.create` (decision 6). The command's origin names the consent (`CommandOrigin.consent_id`, new) and the researcher's request it was approved in (thread and message); the command id derives from (consent, run, seed), so a replay starts nothing. An unset `consent_id` is left out of the receipt and its hash, so earlier receipts still replay | `campaigns/commands.py` `SYSTEM_OPERATIONS`, `_execute`; `contracts/commands.py` `CommandOrigin` |
| The bus guard checks a `balsamic` run against the consent its origin names: in force, its plan lists the proposal, task (or its successor), seed, and no more wall time or evaluations than planned, the id is the planned one, the seed has not run since the go-ahead, and the consent's worker time covers it. The run is charged to that consent and listed in its `launched` | `campaigns/plan_runs.py` `check()`, `charge()`; `campaigns/compute_consent.py` `register()` |
| Never more than the plan: a seed someone already ran since the go-ahead is not run again, and an agent's `trial.create` that would repeat a run Balsamic started (same proposal, task, seed) is refused with a pointer to another seed | `plan_runs.run_of()`, `started_by_balsamic()`; the bus guard |
| When the consent's worker time is spent, launching stops and the lead is told once, under the request the plan was approved in. When every planned run of a consent Balsamic launched for has ended, the lead is woken once: "All N approved runs … finished … Write the comparison (comparison.report)" | `plan_runs._spent()`, `_finished()` |
| The approval card's "Start now" option says Balsamic starts each listed run once its proposal can run; the install box on the coding workspace's card lists the runs Balsamic started; the inbox's install line counts them | `campaigns/commands.py` `approval.request`; `frontend/src/hypotheses/Implementations.tsx`, `workspace.ts`; `src/balsamic/monitor/rows.py` |
| New row INV-B5-1; INV-B4-1 says `balsamic` may also run `trial.create`. `docs/optimizer-plugins.md` says Balsamic starts the approved runs after an install | `docs/invariants.md`, `docs/optimizer-plugins.md` |

## Checked

- `tests/test_plan_runs.py` (6 tests): a plan of 4 proposals × 2 seeds starts nothing before a binding; after an install binds
  two proposals exactly their 4 trials start, with receipts by `balsamic` naming the consent and the request, charged to the
  consent; another sync starts none; the other 4 start when a later install binds their proposals. A planned run of an
  unbound proposal never starts, and a forged `balsamic` run outside the plan (another proposal, an unplanned seed, a
  longer wall time, no consent) is refused. A seed the researcher ran since the go-ahead is not run again, and an agent's run
  repeating Balsamic's is refused. A superseded planned task runs on its successor. With worker time for 3 of 8 runs, 3 start
  and the lead is told once. When all planned runs end, the lead gets exactly one notice, under the request root.
- `tests/test_automatic_binding.py` (`balsamic` still cannot run any other operation), `tests/test_library_install.py`,
  `tests/test_compute_consent.py`, `tests/test_invariants.py`, `tests/balsamic/` pass.
- `frontend/tests/implementations.spec.ts`: the install box lists the run Balsamic started.
- The full suite: see the PR.

## Not done

- Planned runs that name only an algorithm, no proposal, are not started by Balsamic: the lead starts them, as before.
- The lead's instructions and the supervision procedure still say the lead hands approved runs to the operator: B7 rewrites
  them. Until then the lead may also try to start a run Balsamic started; the bus refuses the repeat.
- Runs start at the next workspace sync (about once a minute) after a go-ahead, not at the moment of the go-ahead, unless an
  install binds their proposal first.
- A planned run that cannot start yet is retried at each sync; why it waits is returned by `launch_ready()` but not shown
  on a page.

## Acceptance test

Use a campaign with the lead agent switched on, where you asked for two methods that do not exist in the lab yet (for
example "a dynamic program and an adjacent-swap search for this order"). Until B7, ask for the plan in so many words.

1. In the chat, write: "Implement these two methods and compare them: 2 seeds each, 5 minutes per run. Name the
   proposals and list the runs in the compute request." An approval card appears in the inbox listing the coding workspace
   and the 4 runs. Its "Start now" option says Balsamic starts each listed run once its proposal can run. Approve it.
2. Wait for the coding agent to deliver. Balsamic installs the library and binds the proposals by itself (B4).
3. Without writing anything, open Experiments: the 4 planned runs (2 proposals × 2 seeds) are there, queued or running,
   started by Balsamic. On Hypotheses → Implementations, the workspace's install box shows "started … seed 0 … by Balsamic"
   for each, and the inbox's install line says how many approved runs Balsamic started.
4. Wait a few minutes more: no fifth run appears, and no run is started twice.
5. When all 4 runs have ended, the lead writes in the chat once, saying all approved runs finished, and goes on to the
   comparison. It is not woken again for the same plan.
6. Optional: approve a plan whose worker time covers fewer runs than it lists (for example 2 runs of 5 minutes with 5
   minutes of worker time). Only the runs that fit start, and the lead tells you the go-ahead's time is spent and asks for
   a new one for the rest.
