# L4 — Tests accumulate; kept methods reproduce their recorded runs

State: merged (#106, 2026-10-28), released in `track-l` ([notes](../releases/track-l.md)); not checked live (see the acceptance test).

## What was wrong

Layer: evidence. A new version's validation ran only its own tests, so it could delete an earlier test and change a method it
kept, and campaigns that ran that method would silently run something else under the same name.
Invariant: INV-L4-1, INV-L4-2 (added).

## What changed

| Change | Where |
|---|---|
| Validation outside the box runs every earlier version's test files the new version does not hold unchanged (with the helpers beside them), mounted read-only at `/earlier`, and every earlier workspace's protected tests on the same library beside the workspace's own. A failing earlier test refuses the method it names, or the library; one naming a method the version removed does not count (L1 already refused removing a used one) | `agents/library_validation.py` `earlier_tests()`, `earlier_protected()`, `command()`, `run()`, `verdict()`, `owner_of()` |
| Each kept method and problem replays up to 3 recorded runs (trials of any campaign, their `observations.jsonl`) for the first 8 evaluations inside the sandbox: the method, made by its plug-in with the run's seed and fed the recorded results, must propose the recorded candidates; the problem must evaluate them to the recorded objectives (relative 1e-9). A method that does not is refused, naming the run and the evaluation; a problem that does not refuses the library | `agents/library_validation.py` `recorded_runs()`, `_replays()`, `_same()`, `reproduced()`; `agents/library_install.py` `Installer._validate()` |
| The install records `host_validation.earlier` and `host_validation.reproduced`; its kept line says how many kept methods reproduce how many runs; the install card shows both | `agents/library_install.py` `kept_text()`; `frontend/src/hypotheses/Implementations.tsx`, `workspace.ts` |

## Checked

- `tests/test_library_reproduce.py` (real sandbox): an unchanged method and problem reproduce a recorded run; a method that
  draws one more random number is refused at evaluation 1 of the run; a changed objective refuses the library; an earlier
  version's test of a kept method refuses it, one of a removed method does not count; the host gathers rewritten earlier tests,
  other workspaces' protected tests and recorded runs; an install whose kept method drifted is refused through the installer,
  and the same version with it unchanged installs and says it reproduces the run.
- `frontend/tests/implementations.spec.ts`: the install card shows the earlier tests and the reproduced runs.
- Full runs at the PR's head: see the PR.

## Not done

- Only the first 8 evaluations of up to 3 runs are replayed per method; a change that only shows later in a run is caught by
  the method's own and earlier tests, not by replay.
- Methods whose proposals depend on wall-clock time or outside state cannot reproduce; they fail replay and need a new name
  for each change, which is what decision 25 asks anyway.

## Acceptance test

1. With a package installed and one of its methods run in a campaign, have a coding workspace deliver a new version that
   changes how that method searches but keeps its name.
2. The install is refused: the card says the method does not reproduce its recorded run, naming the run and the
   evaluation where it differs, and says to give the change a new name.
3. Deliver the change under a new method name instead. It installs, and the card says the kept methods reproduce their
   recorded runs.
