# B4 — Proposals are bound to delivered methods automatically

State: implemented and tested (PR pending, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

- **The lead bound every proposal by hand after an install.** Once Balsamic installed a coding workspace's library, the
  install notice told the lead "Bind each proposal to its method (implementation.bind_builtin)", although the method
  catalog already knew which installed method served which proposal. Until the lead noticed and bound them, the proposals
  showed "installed, not bound" and could not run.
- **A binding voided the concept review.** `bind()` rewrites the proposal's `algorithm_config`, which
  `hypothesis_revision()` hashed, so a proposal reviewed before its method was built needed a new review once bound.
- **Nothing could act for Balsamic itself.** The command bus accepted only the researcher, the manager (an agent) and
  autopilot, so an automatic binding had no actor to run under and no receipt to show.

## What changed

| Change | Where |
|---|---|
| The system actor `balsamic` (decision 6): the bus accepts it for `implementation.bind_builtin` only (`SYSTEM_OPERATIONS`; B5 adds `trial.create`), and only when the command's origin names it. `CommandOrigin.actor` gains `"balsamic"` | `campaigns/commands.py` `SYSTEM_OPERATIONS`, `CommandService._execute`; `contracts/commands.py` `CommandOrigin` |
| A binding by `balsamic` cites the install (`install_id`): a completed install of the campaign whose submission serves the proposal and reports that method for it. It never binds a proposal that is already bound. Every binding record now says who bound it (`authority`) | `implementations/builtin.py` `bind()`, `_check_install()` |
| After a successful install, one post-install step, `after_install()`, binds each proposal the submission serves when exactly one of its reported methods is installed and runnable on a current task, through the bus as `balsamic`, with a command id derived from (install, proposal). It skips, with the reason, a proposal someone bound, one that uses another method, a stopped one, one with several candidate methods, and one whose methods are not installed or cannot run on any task. E5 adds adoption before the binding and B5 launching after it | `agents/library_install.py` `after_install()`, `bind_served()` |
| The install record lists `bindings` (proposal, method, task, binding id, command id) and `skipped` (proposal, reason). The notice names both and no longer asks the lead to bind. A failure in this step is recorded on the install (`after_install_error`) and never undoes the install | `agents/library_install.py` `Installer.install()`, `bound_text()` |

| The install box on the coding workspace's card lists what Balsamic bound and what it left, with why; the inbox's install line says how many proposals were bound | `frontend/src/hypotheses/Implementations.tsx`, `workspace.ts`; `src/balsamic/monitor/rows.py` |

## Checked

- `tests/test_automatic_binding.py` (8 tests): a library serving two proposals binds both, with receipts by `balsamic`
  that cite the install, and the notice names them without asking the lead to bind; binding again binds nothing twice. A
  proposal the researcher bound is untouched, and an incompatible method, two candidate methods and a proposal that chose
  another method are each skipped with their reason. A review recorded before the binding stays valid after it, while a
  change to the mechanism is still a new revision. `balsamic` is refused for `trial.create`, `hypothesis.status`,
  `campaign.update` and `approval.request`, and a forged binding (no origin, no install, a method or proposal the install
  did not deliver) is refused.
- `tests/test_builtin_binding.py`, `tests/test_library_install.py`, `tests/test_method_catalog.py`,
  `tests/test_framework_campaign_commands.py`, `tests/test_asked_for_proposals.py`, `tests/test_invariants.py` pass.
- `frontend/tests/implementations.spec.ts`: the install box shows the bound and the skipped proposals.

## Not done

- Runs do not start by themselves after the binding: that is B5, which adds `trial.create` to `SYSTEM_OPERATIONS` and its
  step after the binding in `after_install()`.
- The lead's instructions and the supervision procedure still mention binding by hand: B7 rewrites them. The method
  catalog still names "bind" as the lead's next step for a proposal Balsamic skipped, which is still right for those.
- A binding uses the method's default parameters and the first current task it runs on.
- After a binding, an edit of the proposal's `algorithm_config` (the method's parameters) no longer makes a new review
  revision; a change to its title, mechanism, rationale or parents still does.
- A library whose methods appear in the running lab more than a second after its install finishes (the plug-in registry
  re-checks at most once a second) is skipped as "not installed"; the lead can still bind it by hand.

## Acceptance test

Use a campaign with the lead agent switched on, where you asked for two methods that do not exist in the lab yet (for
example "a dynamic program and an adjacent-swap search for this order"), and approved the coding workspace.

1. Wait for the coding agent to deliver. Balsamic installs the library by itself, as before.
2. Open Hypotheses → Implementations and find the workspace's card. Its install box says "installed", lists the new
   methods, and under them shows each proposal as "bound … → <method> by Balsamic". You did nothing to bind them, and the
   lead was not asked to.
3. Open each of those proposals on the Hypotheses page. Each runs its new method and says it can run; if a reviewer had
   judged it before, its review still shows and is not "pending" again.
4. Before a later delivery of the same workspace, ask the lead to bind one of its proposals to another installed method.
   After the next install, the install box lists that proposal as "not bound" with "Already bound to …", and the
   proposal keeps the method the lead bound.
5. In the inbox, the install line says how many proposals Balsamic bound.
