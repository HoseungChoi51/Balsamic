# F4 — Coding workspaces start from the generated library

State: implemented and tested (PR pending, 2026-10-27); the live check is the acceptance test below.

## What was wrong

Layer: none: a missing capability, not a failure at a layer.
Invariant: INV-F4-1 (new).

- A coding workspace's brief was the first proposal's JSON (`record["hypothesis_id"]`) and `DEVELOPMENT_INSTRUCTIONS`,
  although the workspace may serve several proposals (`hypothesis_ids`). The coding agent got no charter.
- `DEVELOPMENT_INSTRUCTIONS` told it to copy `libraries/grating-mask-search` and named `/references/flrl` and the paper,
  whatever the problem: a new problem's agent started from a grating library.
- The library generated from the charter (F1, F3) was never handed to the coding agent, so each workspace wrote the
  problem's data and harness again by hand, and nothing checked that the delivered library still held the charter's data.

## Checked

- `tests/test_development_generated_library.py` (12 tests): a workspace of the ovens charter's campaign writes the
  generated library byte for byte into the worktree, records the generated files' hashes on the record and in
  `prepared.json`; prepared again (its `prepared.json` lost), it keeps an edited `harness.py`, writes back a removed
  `README.md`, and records the same hashes. The brief lists both served proposals with their `METHODS` keys and
  mechanisms, the charter's summary and objective, the library's path, and no "grating", "flrl" or "paper". A campaign
  without a charter gets no library and still lists its proposals; a charter without an evaluator gives no library and
  the brief says why. Method keys are method ids, unique among the proposals. References are named only when present.
  `DEVELOPMENT_INSTRUCTIONS` is shorter than at `cc0e693` in words and characters and names no grating library or
  reference. With a real Git store and a faked uv: a delivery with an edited `harness.py` installs and lists only it; an
  edited `data.py` or `charter.json` is refused before anything changes, and Balsamic's own install records the
  refusal; a library the workspace did not generate is not compared.
- `tests/test_pi_development_workspaces.py`, `tests/test_library_install.py`, `tests/test_automatic_binding.py`: unchanged
  and passing.
- Playwright `implementations.spec.ts`: the install box names the changed generated files.
- Full suite with `-n 4`, the launcher's tests as user `claude`, `npx tsc -b`: counts in the PR.

## Not done

- Two workspaces of one campaign both start from `libraries/<problem-id>/` with the same project name, so the second
  delivery replaces the first's methods unless it keeps them. The lead is expected to open one workspace serving all the
  proposals (`hypothesis_ids`), as the brief now supports; separate libraries per workspace are not done.
- The fake driver writes the library where the Docker driver would; the Docker path (`DockerWorkspace.prepare`) is not
  run in the cloud tests (no Docker), so the acceptance test is its check.
- The manifest is still needed: the worktree holds the lab's own `libraries/grating-mask-search` as well, so a manifest
  cannot be derived from the commit's single library.
- A charter revised after the campaign was made is not followed: the workspace starts from the campaign's revision.

## Acceptance test

1. Start the app. Create a campaign from a confirmed charter whose evaluator is declared (for example one made from an
   example problem), and give the team the go-ahead to implement two of its proposals in one coding workspace.
2. Open the coding workspace's editor. Expected: `libraries/<problem id>/` holds the generated project (`charter.json`,
   the package with `data.py`, `objective.py`, `methods.py`, `adapter.py`, and `tests/`).
3. Open `.campaign/assignment.md`. Expected: it names the problem and its objective, lists both proposals with the
   `METHODS` key for each, and mentions no grating library, `flrl` or paper unless such references were supplied.
4. Let the coding agent deliver. Expected: on the Implementations page the install succeeds and the proposals' methods
   appear; if the agent changed a generated file other than the objective and the methods, the install box lists it
   under "changed from the generated library".
5. Ask the coding agent (through the workspace chat) to change a value in `data.py` and deliver again. Expected: the
   install fails with "The library's data no longer matches the charter revision", and the lab keeps the earlier
   version.
