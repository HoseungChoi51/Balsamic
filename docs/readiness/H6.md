# H6 — Validation outside the box

State: implemented and tested (PR #67, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

Layer: evidence. What entered the lab rested on the coding agent's own report: nothing outside the box ran the library's
tests or its methods' conformance.
Invariant: INV-23 (updated).

- **The install trusted the coding agent's report.** `Installer.prepare()` checked the commit's files against the
  submission and installed them, but ran none of the library's tests; "ready" meant the coding agent said every method's
  conformance passed. A method reported as passing was installed and bound whether or not it held the contract.
- **Protected acceptance tests existed only for commissions** (`implementation_workspace_validate`), not on the library
  route.

## What changed

| Change | Where |
|---|---|
| Before an install counts (Balsamic's own or the researcher's), the host validates the exact commit's `libraries/<name>/` in a bubblewrap sandbox with no network, no host environment, the system and the lab's Python read-only, nothing of the lab's data, and only a result directory writable: the library's own tests (the generated contract tests among them, F3), conformance for each method (`check_function` for a plain-function method, `check` for any other) and the workspace's protected acceptance tests. The install's status is `validating` meanwhile | `agents/library_validation.py` `run()`, `command()`, `main()`; `agents/library_install.py` `Installer._validate()` |
| The sandbox starts the lab's interpreter. The draft's could not (`execvp /usr/bin/python3: No such file` with a merged `/usr`: the venv's python reaches its binary through `/etc/alternatives/python3`, which was not bound). It now binds the environment and its installation, and each link of the interpreter's symlink chain outside them by itself, as `agents/files.py` `interpreter()` follows the chain, but not the rest of `/etc`. It runs the host's own Balsamic (`PYTHONPATH`), so what validates a library is the Balsamic that installs it | `agents/library_validation.py` `roots()`, `links()`, `source()` |
| Conformance runs on the campaign's tasks on a problem the library provides, then the library's own problems at their defaults, then the campaign's other tasks: the first a method runs on. A plain-function method falls back to a problem and representation it names, explicit constraints left to `check_function()`, as the library's generated contract test runs it | `agents/library_validation.py` `_instances()`, `_fits()`, `_conformance()` |
| The verdict: a method whose conformance fails, or one of whose tests fails (a test parametrized with its id, the library's or a protected one), is refused; a failed test no method owns (a broken objective, a collection error) is the library's, and nothing is installed | `agents/library_validation.py` `verdict()` |
| The install record carries the host's results beside the coder's report (`host_validation`: the test counts and each test's outcome, each method's reported and host conformance with the check and the problem, the protected tests by name and outcome) and the methods it refused (`refused_methods`, each with what failed). A refused method is left out of `methods_added` and not bound, and the methods that pass are installed beside it; the install notice to the lead names both | `agents/library_install.py` `Installer.install()`, `refused_text()`, `bind_served()` |
| A refused method does not run: binding it (`implementation.bind_builtin`, the researcher's too) and starting a run of it on the lab's code are refused with what failed, and the Algorithms list gives that reason, until a version that passes is installed. Reproductions of captured code and frozen prototypes are not affected | `agents/library_validation.py` `refused_reason()`; `implementations/builtin.py` `bind()`; `execution/service.py` `Workspace.create_trial()`; `campaigns/method_catalog.py` `catalog()` |
| The coder gets the results once per install: a result file in the box (`incoming/results/host-validation-<install>.json`) and one message naming what failed. Protected tests appear there, and on the install, by name and outcome only | `agents/library_install.py` `Installer._feedback()`; `agents/library_validation.py` `public()` |
| Protected acceptance tests are kept on the host with the workspace (`development_protected_test` records), never written into the worktree or mounted in the box | `agents/library_validation.py` `protect()`, `protected_tests()` |
| Validation's time is charged to the go-ahead the workspace opened under: the consent that is its request's mandate's compute part | `agents/library_install.py` `Installer._charge()` |
| The install card says what was checked outside the box (tests, conformance, protected tests) and lists each method not installed with what failed; "checking outside the box" shows while it runs | `frontend/src/hypotheses/Implementations.tsx` `HostValidation`, `InstallBox`; `frontend/src/hypotheses/workspace.ts` |

## Checked

- `tests/test_library_validation.py`, with the real sandbox:
  - the ovens' generated library passes on the host: its tests, and `check_function` for each method on its own problem;
  - a method reported as passing that proposes an invalid candidate is refused with the failing check named, even when the
    coder emptied the library's own tests; with its tests, each failing test is named on the method;
  - the sandbox reaches no network, sees none of the host's files and cannot write the library;
  - the verdict assigns each failing test to the method in its id and the rest to the library, and the coder's view of
    protected tests has names and outcomes only;
  - through the install: a library that passes everything installs as before, and nothing is sent to the coder; with a broken
    method and a protected test, the method is not installed, binding it and starting a run of it are refused, the other
    methods are installed, the protected test's outcomes are on the install by name only, its source and failure text are
    nowhere in the box, and the coder gets one result file and one message (once, on a replay too); a library failing in a
    test no method owns installs nothing; validation's time is charged to the workspace's go-ahead.
- `tests/test_baking_order_e2e.py`: with the real validator, the generated baking-order library passes on the host (its
  tests and each of the four methods), then installs, binds and runs its 8 approved runs as before.
- `tests/test_library_install.py`, `tests/test_development_generated_library.py`: a stub validator, since their libraries
  are fakes (or deliberately edit generated files); everything else as before.
- `frontend/tests/implementations.spec.ts`: the card says what was checked outside the box and names the method not
  installed with what failed.
- Full runs at the PR's head: see the PR.

## Not done

- Nothing writes protected tests yet: the ticket (H4) will. They are stored with the workspace (`protect()`), and every
  delivery of that workspace runs them.
- A method whose conformance could not run on the host (no problem of the library or task of the campaign it runs on) is
  installed and listed as `not_run`; it cannot be bound in this campaign anyway.
- The sandbox needs bubblewrap on the host, as the worker sandbox does; without it every install fails and says so. pytest
  must be in the lab's environment (`uv sync --extra dev`, as the README says); without it the library's tests count as
  failed and nothing is installed.
- Validation's time is charged to the go-ahead without asking first when it is longer than what is left (the phase's risk);
  it is bounded at 10 minutes and 4 GB of address space.
- The validation runs on the host's Python and packages, not in the worker's per-run captured runtime
  (`execution/isolation.py`).
- A refused method's code is still in the installed package (uv installs the library as a whole); it is refused where it
  would be bound or run.

## Acceptance test

Use a lab with coding workspaces switched on and a campaign whose charter generates a library (the baking order works),
with the lead agent on.

1. Ask the lead to build two methods in a coding workspace and approve its card. When the coding agent delivers, open
   **Proposals → Implementations**. The install should show **checking outside the box**, then **installed**, with a line
   "checked outside the box N tests passed · conformance passed for 2 of 2 methods", and the proposals bound as before.
2. Ask the lead to have the coding agent add a third method that is deliberately wrong (for example "a method that sets
   every value to one the charter does not allow, and report it as passing"). After its delivery the install should still
   be **installed**, with the line in red and the third method under **not installed**, followed by the check that
   failed. The first two methods should still run.
3. Open the **Algorithms** list: the third method should say it failed validation outside the box. Asking the lead to run
   it should be refused with the same reason.
4. Open the workspace's editor: `ls incoming/results` in its terminal should show a `host-validation-…json` file naming the
   failed method, and the coding agent's history should show one message from Balsamic saying what to fix.
