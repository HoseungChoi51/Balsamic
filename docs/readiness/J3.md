# J3 — Partnership metrics

State: implemented and tested (PR #45, 2026-10-27); the protocol's first run is Hoseung's.

## What was wrong

Layer: none. The part fixes no failure; it adds a measurement that later phases are judged by.
Invariant: none, it adds no guarantee: the metrics are a reading of records, pinned by their own tests.

- The monitor showed compute and model spend per campaign only. Nothing said, per researcher request, how much the
  researcher had to do, how long it took, what it cost and how good the result was by then.
- So "does the researcher do better with the agents than alone" (the original plan's Increment D, design review sections 02,
  04 and 05) could not be answered, and Phase 7's parts had no partnership number to keep or revert by.

## What changed

| Change | Where |
|---|---|
| Partnership metrics. A request is a lead turn a researcher message started (decision 7: not autopilot, not a notice). Its work is every turn whose request root names it (the lead's notice turns, the turns of agents assigned for it) and every command those turns sent. Per request: the researcher's commands from the message to the report (messages, decisions resolved, other commands; a decision's own effect is not counted again); seconds to the lead's report (the first of its lead turns that ended with `yield_work(complete)`) and to the first `comparison.report` its work made; the runs its commands started (a race's runs included) and their measured worker seconds; its model calls, each given to the turn its agent was in, with list-price and charged dollars; the best objective of any run in the campaign that finished by the report (or by now, while open), in the objective's direction with A2's `best_of`. Unknown is None, never zero | `src/balsamic/monitor/partnership.py` |
| An agent turn records `finished_at` when it ends; turns from before take the time of their terminal update from the event log | `agents/controller.py` `_receive()` |
| `GET /api/v1/campaigns/{id}/partnership`: the rows and how each number is measured | `src/balsamic/api/monitor.py` |
| A Partnership tab on the Monitor page: one row per request, with the actions, the two times, worker time and runs, model dollars and the best by then ("lower is better" when minimizing); "open" and "not reported" while the request is open | `frontend/src/monitor/MonitorPage.tsx`, `frontend/src/router/pages.json` |
| The protocol Hoseung runs once per phase: the same small problem solved alone (a local coding agent on the Python project) and with Balsamic, the same four numbers for both, and a results table | `docs/evals/partnership.md` |
| The Monitor's partnership paragraph, and the protocol in the docs index | `docs/ui-workspace.md`, `docs/README.md` |

## Checked

- `tests/balsamic/test_partnership.py` (4 tests): a seeded campaign with two requests. The first has a turn, a notice turn
  that continues it and reports, a run, a race with a run, a comparison report, a decision and a command from the
  researcher, and model calls on both turns: 3 researcher actions (the decision's own effect is not counted), 600 s to the
  report and 500 s to the ranked result, 2 runs and 65 worker seconds (the researcher's own run is not the request's), 3 calls
  at $0.17 list price and $0.15 charged, and the best by the report is the lowest value that had finished (1.5), not a lower one
  that finished later. The second request is open: no report time, its own model call, and the best by now (0.5). On a
  maximize problem the highest value is best; an autopilot turn opens no request. A turn without `finished_at` takes its end
  from the event log. The route serves the table and 404s for an unknown campaign.
- Playwright `monitor.spec.ts`: the Partnership tab shows both rows, their times, runs, cost, "lower is better", and "open",
  "not reported" and "unknown" for the open one. `npx tsc -b` passes.
- Full suite: see the PR for the counts at its head.

## Not done

- The protocol's first run (alone and with Balsamic) is Hoseung's; its results table is empty until then.
- Researcher actions are counted in a time window, so requests open at the same time each count the actions in their window.
  The protocol says to send one request at a time.
- The best is campaign-wide by the report, not limited to the request's runs; a campaign with tasks of different directions
  has no single best (shown as none). Implementation grants (the old evaluator-commissioning path) are not in a request's
  model dollars.
- Phase 1's "alone" bar needs F2's export of the Python project; until it lands, the protocol uses the problem's own module.

## Acceptance test

1. Start the app and open a campaign whose agent team is active (the lead answers in the main chat).
2. Send the lead a request, for example: "Run a short random search and tell me the best value." Wait until it reports.
3. Open Monitor → Partnership. A row shows your request's text, "Your actions" at least 1 (your message), a "To report" time,
   the worker time and number of runs it started, the model dollars, and "Best by then" with "lower is better" or "higher is
   better" matching the problem.
4. Send a second request and open the tab again while the lead is still working: a second row says "open" and "not
   reported". When the lead reports, it gets its own time.
5. If you resolve a decision or approve something while a request is open, its "Your actions" goes up by one.

Live eval: once per phase, run the protocol in [docs/evals/partnership.md](../evals/partnership.md) at the phase's release
tag and fill its results table: the same small problem alone with a local coding agent and with Balsamic, the same four
numbers for both.
