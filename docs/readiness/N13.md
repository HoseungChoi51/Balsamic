# N13 — Bounds and optimality

State: implemented and tested (PR to come, 2026-10-28); the acceptance test below is Hoseung's.

## What was wrong

Layer: evidence. A run's result was only its best value so far. An exact method's proof of optimality, or a bound from
branch and bound or a solver, had nowhere to go, so "proved 412 optimal" and "found 412" looked the same, no page could
show how far a result might be from the optimum, and nothing exact was available as a baseline, not even enumeration on a
small instance.
Invariant: INV-N13-1, INV-N13-2 (added, in `docs/invariants/N13.md`).

## What changed

| Change | Where |
|---|---|
| A method reports `bound` and `proved_optimal` in `inspect()` (at any time, and in its final inspection, A3); a function method returns `{"reason", "bound", "proved_optimal"}`. The worker copies the latest to the run's progress as `best_bound` and `proved_optimal`, kept across checkpoints and continuations | `execution/worker.py` `progress()`, `save_checkpoint()`; `optimizers/functions.py` `FunctionMethod` |
| Built-in `enumerate`: every candidate of a binary, discrete or permutation problem in a fixed order, infeasible ones skipped, refused above `max_candidates` (default 10⁶) with the count. On an oracle problem one evaluation per candidate; on a white-box problem it enumerates through `problem.objective` and records only the optimum. It finishes with the optimum as its bound and `proved_optimal` | `optimizers/enumerate.py`; `optimizers/registry.py` (`BUILTINS`, `validate_parameters()`, `create()`); `optimizers/lifecycle.py` `AskTellAdapter.open_objective()` |
| A claim of optimality is checked (enumeration finished on the task with the same optimum, or a charter reference result with the same value at the task's instance), contradicted (a run's best beats it) or claimed by its method. Per task: the best value, the tightest bound no run beats, the gap absolute and relative to the bound | `analysis/optimality.py` `summarize()`, `charter_references()`, `by_task()` |
| The comparison report: each group has `optimality`, each run row `best_bound`, `proved_optimal` and, with a checked optimum, `optimum_reached_at`; methods that reached a checked optimum rank first by their mean cost to it (`cost_to_optimum`) | `analysis/general.py` `report()`, `rank_by_optimum()` |

| The contract checks refuse a method whose own best beats the bound it reports | `optimizers/conformance.py` `check()`, `check_function()` |
| The Evolution page's Frontier: a "Bounds and optimality" table per task (best value, best bound and who gave it, gap, the optimum as proved or as a claim) and a badge on each strategy's best ("proved optimal", "optimal: claimed by …", "optimality claim contradicted") | `frontend/src/evolution/EvolutionPage.tsx`, `frontend/src/api/evolution.ts` |
| The knapsack benchmark can be a campaign task: its resolved configuration (with the items' weights and values) resolves again to the same instance | `optimization_benchmarks/problems.py` `KnapsackConfig` |
| `docs/optimizer-plugins.md` "Bounds and optimality" | docs |

## Checked

- `tests/test_bounds_and_optimality.py` (6 tests): `enumerate` on the 8-bake tardiness instance (C2's) visits all 40,320
  orders on an oracle problem and makes one evaluation on a white-box one, finishing with the enumerated optimum as its
  bound and proof; a checkpoint part way continues the same order; it is refused on 2⁴⁰ candidates with the count, and on
  continuous candidates; it meets the contract checks, and a bound its own best beats fails them; a proof that
  enumeration beats is contradicted, not proved, a proof nothing checks is claimed, a reference result checks one, and a
  bound a run beats is not the best bound; on a 12-item knapsack campaign, enumeration, a dynamic program that proves
  its optimum and a greedy rule that wrongly claims one give a report with gap 0, the optimum checked by enumeration, the
  greedy claim contradicted, and the two exact methods ranked first by their cost to the optimum; a charter reference
  result applies to the task whose instance it holds at.
- `tests/balsamic/test_optimality_ledger.py` (2 tests): the Evolution API's per-task bound, gap and optimum; each
  strategy's proof (checked, claimed, contradicted, none); a checked proof makes its strategy extended and refuses it more
  time, a replicate still allowed; an unchecked proof stays in screening.
- `frontend/tests/optimality.spec.ts` (2 Playwright tests): the Bounds and optimality table and the proof badges; no
  table when nothing reports a bound.
- The full suite (counts in the PR).

## Not done

- "Deterministic" is read from the evaluator (`evaluator_manifest.deterministic`, true unless a declared problem says
  otherwise); methods declare no determinism of their own. A checked proof holds for every seed, so the method's seed is
  not asked about.
- `enumerate` on a white-box problem computes every candidate in one step, so a pause or the wall budget takes effect
  only after it; the 10⁶ cap keeps that step bounded.
- V3's finalist gate is unchanged: a claim of optimality is a score like any other there until Phase 7's K track resolves
  claims to their receipts. The legacy grating analysis (`analysis/comparison.py`) is unchanged; MEENT's methods report
  no bounds.
- The Hypotheses card shows the claim only through the ledger row; the run's own page does not show its bound yet.

## Acceptance test

1. Start the app and open a campaign on a small problem whose candidates can be counted, for example a baking order of
   8 bakes (a permutation) or a knapsack of about a dozen items. Ask the lead (or use the Experiments page) to run
   "Enumerate every candidate" on it. The run completes on its own (method finished), and its result is the optimum.
2. Run a heuristic too (random or swap search) on the same task. Open Evolution → Frontier: a "Bounds and optimality"
   table shows the task with its best value, a best bound from enumerate, a gap of 0, and "proved, checked by
   enumeration". The enumerate strategy's best has a green "proved optimal" badge.
3. Select the enumerate strategy and choose "Allocate time…": the page says it proved the value optimal and more time
   cannot improve it.
4. On a problem too large to enumerate (a knapsack of 40 items, or 12 bakes), asking for "Enumerate every candidate" is
   refused with the number of candidates.
