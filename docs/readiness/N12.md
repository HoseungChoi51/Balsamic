# N12 — Problem-owned candidates

State: implemented and tested (PR pending, 2026-10-28); the acceptance test below is Hoseung's.

## What was wrong

Layer: evidence. A candidate was a flat vector: binary, discrete, continuous, or one order of items. A problem whose
solution is an order of jobs per machine, several orders, a sequence of variable length, a set, a tree or a graph had no
form, and neither did rules such as "every job runs exactly once on some machine". Such a problem had to be squeezed into
a vector that the evaluator decoded and repaired, and nothing kept a method from spending evaluations on candidates the
rules forbid.
Invariant: INV-N12-1, INV-N12-2, INV-N12-3 (added, in `docs/invariants/N12.md`).

## What changed

| Change | Where |
|---|---|
| A representation `structured`. The candidate is one JSON value. The schema's `structure` names its owner (the problem's id), its `meaning` and `layout`, the `fields` the library derives for design constraints, and the instance's public configuration as `context`. `canonicalize` stores and hashes the value the library's `canonicalize` gives, and refuses one its `is_valid` finds a broken rule in or that breaks a design constraint over the fields. It checks nothing else. Schemas without it dump as before | `contracts/problems.py` `Structure`, `StructureRules`, `register_structure()`, `structure_rules()`, `CandidateSchema._structured()`, `broken()`, `describe()` |
| The library's rules are registered under the problem's id where its code runs. A process without them looks the problem up among the installed problems (`structure()` on its adapter), and otherwise refuses the candidate with a reason | `contracts/problems.py` `structure_rules()`; `problem_charter/library.py` `CharterProblem.structure()`, `CharterStructure` |
| A charter may declare one `structured` decision variable, with a meaning and a layout (required), no shape, bounds or values, and optional `fields`. Its rules are constraints of form `evaluator`, or `design` expressions over the fields. Findings: it must be the only variable and described, a linear constraint on it is refused, and a design constraint reads its fields, not the value | `contracts/problem_charter.py` `DecisionVariable`; `problem_charter/charter.py` `structured_findings()`, `design_findings()`, `constraint_findings()`, `manifest()`, `compare_provided()` |
| Built-in methods refuse it: "the problem's library owns this representation; use a library method". A function method's `problem` has `is_valid`, `violations` and `canonicalize`, which use the library's rules | `optimizers/registry.py` `capability_reason()`; `optimizers/functions.py` `CheckedProblem` |
| The generated project has a third file to fill, `structure.py`, with `canonicalize`, `is_valid`, `describe`, an optional `random_candidate` and `fields`, and `EXAMPLES`. Its `Problem`, harness and tests take a structured candidate as one value, and a new generated test checks that a valid example (from `EXAMPLES` or a reference result) passes `canonicalize` and `is_valid` | `problem_charter/scaffold.py` `_structure()`; `problem_charter/scaffold_files/` `problem.py`, `harness.py`, `test_problem.py`, `methods.py` |
| The Charter page shows a structured variable's layout | `frontend/src/note/CharterPanel.tsx` |
| The formulator's guideline says when to use `structured`; `docs/optimizer-plugins.md` "Problem-owned candidates" records the rule of two for named types (decision 24) | `problem_import/guideline.md`, docs |

## Checked

- `tests/test_structured_candidates.py` (8 tests). A parallel-machine scheduling fixture (an order of jobs per machine)
  canonicalizes equal schedules to one form. It refuses a schedule that drops a job or uses too many machines, and one
  that breaks the shift rule, a design constraint over the library's `loads` field. Two function methods pass
  conformance, and the worker runs one to completion and records the canonical schedule. A method's descriptor carries
  the library's rules. `random`, `enumerate`, `replay`, `hillclimb` and `coordinate` are refused with the reason above.
  The charter compiles to a manifest, and a change to the meaning or the layout changes its digest. The findings keep the
  variable alone and described. The schema refuses a candidate whose rules are not loaded. The generated project passes
  its own tests, including the new example test and Balsamic's contract test.
- `tests/test_design_constraints.py`, `tests/test_problem_charter*.py`: unchanged and passing.
- The full suite (counts in the PR).

## Not done

- No named types (assignment, set, graph) in the core. A problem that needs one uses `structured`. A type is added only
  when two problems need it (decision 24).
- A structured candidate is checked only where the problem's library can be loaded. A server process that checks one
  (a declared reference solution, say) imports the library's `structure.py` through its installed adapter. Without an
  installed library it refuses the candidate.
- The rules see the instance's configuration only, not its fidelity.
- The Charter page shows the layout but offers no editor for a structured value; the review pages show the candidate as
  JSON.
- The library's own `Problem.is_valid` does not check design constraints over its fields. As with N9, the framework
  checks them before each evaluation.

## Acceptance test

1. Start the app, create a campaign and describe a problem whose solution no vector states, for example: "four jobs
   of 3, 5, 2 and 4 minutes on two identical machines; every job runs once; each machine must finish within a 9-minute
   shift; minimise the makespan".
2. Open the Charter page. There is one decision variable, structured, whose layout reads like "a list with one list per
   machine, each the jobs it runs in order". "Every job runs once" is a rule the evaluator checks, and the shift is a
   design rule over the machines' loads. No check asks to rewrite the schedule as numbers.
3. Confirm the charter and let the coding agent fill the library: `structure.py` (how a schedule is read and checked)
   and the objective. Ask for "Uniform random" on it: it is refused with "the problem's library owns this
   representation; use a library method".
4. Run one of the library's methods. Every evaluated schedule runs each job once and fits the shift, and two schedules
   that differ only in which machine is listed first are recorded once.
