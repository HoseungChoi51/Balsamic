# H1 — The workspace bridge as an MCP server and a CLI

State: implemented and tested (PR pending, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

Layer: none: no failure is fixed. Only Pi could talk to Balsamic from the coding box: the two tools that report progress
and deliver a commit (`campaign_checkpoint`, `campaign_submit`) exist only inside the Pi extension, so no other harness
(H2's adapter, H3's own session) had a way in.
Invariant: INV-H1-1 (added).

## What changed

| Change | Where |
|---|---|
| `balsamic-workspace`, a dependency-free Node CLI and stdio MCP server (newline-delimited JSON-RPC: `initialize`, `tools/list`, `tools/call`, `ping`) with five tools: `checkpoint`, `ask` (a checkpoint carrying a question, which the host already turns into a pending question and a notice), `submit <commit>` (waits for the host's answer as the extension does), `check` (runs `python -m pytest` on the library, from the argument or from `implementation-manifest.json`'s files, and returns the counts, the contract tests' counts apart and the conformance: `failed` when a `test_contract` test fails, `not_run` when there is none), and `evidence` (lists `.campaign/evidence.json` or reads one entry by id, and refuses any other id) | `deploy/implementation-workspace/balsamic-workspace.mjs` |
| It writes the extension's event files (same name format, same `type` and `payload`) into the same bridge, and checks arguments against the extension's own schemas, written as JSON Schema; the host side is unchanged | same file, `emit()`, `TOOLS`, `validate()` |
| The image installs it as `/usr/local/bin/balsamic-workspace`; the host also mounts the repository's copy read-only over it, as it does the extension, so a fix reaches a box without a rebuild | `deploy/implementation-workspace/Dockerfile`; `agents/development_runtime.py` `DockerWorkspace.start()` |
| The extension is unchanged except a comment pointing at its twin | `agent-harness/extensions/implementation.ts` |
| INV-H1-1 records the guarantee; the workspace plan describes the CLI | `docs/invariants.md`, `docs/pi-implementation-workspace-plan.md` |

## Checked

`agent-harness/test/workspace-cli.test.mjs` (6 tests):

- For the same inputs, the CLI (by flags, and by `--json -` on stdin) and the extension write identical checkpoint events;
  `ask` writes what the extension writes for a checkpoint with that question.
- `submit` writes the extension's submission event (the default manifest path included) and prints the extension's own
  answer text from the host's result file, the ignored manifest fields included.
- The CLI refuses a checkpoint without a summary, an unknown phase, malformed test counts, a short commit, a report with
  no methods, an empty question and an unknown command, naming the field, and writes no event.
- The MCP server answers `initialize`, lists exactly the five tools, whose `checkpoint` and `submit` schemas and
  descriptions equal the extension's, writes an event on `tools/call`, returns `isError` with the field for bad
  arguments, and refuses an unknown method with -32601.
- `evidence` lists and reads the given entries and refuses an id not among them.
- `check` on a library with two contract tests and three of its own (one failing, one skipped) reports 3 passed,
  1 failed, 1 skipped and conformance passed; a failing contract test gives `failed`, none gives `not_run`; with no
  library named and none in the manifest it asks for one.

`tests/test_workspace_cli.py` (1 test) runs the CLI against a real `DevelopmentWorkspaces` through the bridge layout of
the container: its checkpoint sets the workspace's phase, tests and estimate, its question becomes a pending question,
and its submission is captured with its delivery report and answered with the submission id.

The harness suite, the development-workspace tests and the full Python suite pass (counts in the PR).

## Not done

- Pi still uses the extension, and nothing tells it about the CLI: wiring a harness to the MCP server is H2 (the
  adapter) and H3 (bring your own session). The coding agent's brief is unchanged, so no prompt text was added.
- `check` returns the counts but sends nothing: the coding agent puts them in its checkpoint or report. Validation
  outside the box is H6.
- The MCP server serves tools only (no resources or prompts) and does not implement cancellation of a pending `submit`.
- The workspace image must be rebuilt (`deploy/implementation-workspace`) for the `balsamic-workspace` command; until then
  the mounted script runs as `node /opt/workspace/balsamic-workspace.mjs`.

## Acceptance test

Before: rebuild the coding-workspace image and restart the lab with coding workspaces on, as for any workspace change.

1. In a campaign with the lead agent on, ask the lead to open a coding workspace for a proposal (approve the go-ahead it
   asks for).
2. On the Proposals page, open **Implementations** and find the workspace under **Coding workspaces**. In **Message the
   coding agent**, write: "Run `balsamic-workspace checkpoint --summary 'Bridge check from the CLI' --phase orienting
   --eta 30` in the shell, then `balsamic-workspace evidence`, and tell me what each printed." Send it.
3. Within a minute or two the workspace card's latest checkpoint should read "Bridge check from the CLI", its phase pill
   should say "orienting", and its estimate 30 minutes; the **History** should show the checkpoint. The coding agent's
   reply should list the evidence the workspace was given (or say none was given).
4. Write: "Run `balsamic-workspace ask 'Is this question reaching the researcher?'`." The question should appear on the
   workspace as a question waiting for an answer, and the lead should be told about it, as for a question the agent asks
   with its own tool.
5. Nothing else about the workspace should change: the coding agent still checkpoints and submits with its usual tools.
