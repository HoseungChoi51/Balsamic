# B2 — A consent names what it covers

State: implemented and tested (PR #4, 2026-10-27); not checked live (see the acceptance test).

## What was wrong

- **A go-ahead covered any work in the campaign.** `covering()` returned the first consent with time left, so the time left
  over from one plan paid for work the researcher never saw: a plan approved for H1–H4 also started a run of H5.
- **Nothing recorded what a go-ahead was for.** `grant()` kept the plan's text, its times and its number of coding
  workspaces, not the proposals or the runs (although the request carried `runs`), and `charge()` counted seconds without
  saying what they bought.
- **A consent expired while its workspace was still building.** It ended `max(3600, 3 × wall_seconds)` after the grant,
  so a coding workspace that built for longer lost the go-ahead for the validation and runs that followed.

## What changed

| Change | Where |
|---|---|
| A compute request names the proposals it is for (`hypothesis_ids`, compute only, each a proposal of this campaign); the approval card says the go-ahead covers only their work | `contracts/commands.py` `ApprovalRequestInput`; `campaigns/commands.py` `approval.request` |
| A consent stores those proposals with those its runs name, the runs, the researcher's request it was asked in (the request root of the asking turn) and empty `workspace_ids` and `launched` | `campaigns/compute_consent.py` `grant()`; the request root on the decision |
| A consent that names proposals covers a workspace, run or commission only when it names every proposal the work is for, and work for no proposal (a runtime profile, an analysis) only in its own request. One that names none covers anything, as every consent recorded before | `compute_consent.covers`, `covering`, `require`, `proposals`, `request_root` |
| The callers pass the proposals: the bus guard and listener (the payload's, a draft's, a continued run's, a race's, a batch's), `development.create()` (the served proposals), the validation of a submission (the workspace's), an analysis script (its agent's request) | `compute_consent.register`; `agents/development.py` `create`, `validate`; `agents/files.py` `analysis_run` |
| `charge()` records the coding workspaces and the runs it paid for | `compute_consent.charge` |
| A refusal lists the approved plans that cover the work, or says that none does and what each covers | `compute_consent.refusal` |
| A consent stays in force while a workspace it opened runs, and for 3 × its wall time after the last one stops; a pause at the CPU allowance records when it stopped | `compute_consent._in_force`; `agents/development.py` `sync` |
| INV-01 now says what a plan covers, pinned by the new tests | `docs/invariants.md` |

## Checked

- `tests/test_compute_consent.py`: a plan for H1–H4 (three named, one by its run) does not cover a run of H5 and the refusal
  names the plan and what it covers; a run of H1 is charged to it and recorded; a second plan for H5 covers H5; work for no
  proposal is covered in the plan's own request (the asking turn, a notice turn continuing it, an assistant given it) and
  not in another; a consent recorded before this change covers the whole campaign; `charge()` records the workspace and the
  trial ids; a consent outlives its expiry while its workspace builds and ends 3 × its wall time after the workspace stops.
- `tests/test_pi_development_workspaces.py`: a lead opens a workspace only for the proposals the go-ahead names, and the
  consent records it.

## Not done

- The lead's instructions do not yet say to name the proposals in a compute request: B7 rewrites them. Until then a lead's
  request names none and covers the campaign, as before.
- Runs that start by themselves under a consent (B5) and the mandates that replace consents (Phase 3) build on this.

## Acceptance test

Use a campaign with at least two proposals (call them A and B) and the lead agent switched on. Leave the go-ahead
threshold at its default of 5 minutes. Until B7 the lead is not told to name the proposals in its request, so in step 1
ask for it in so many words.

1. In the chat, write: "Run proposal A for 10 minutes, and name proposal A in the compute request." An approval card
   appears in the inbox. Below the plan and "Meanwhile" it should say "It covers only the work for" and A's id.
   Approve it with "Start now". A's run should start, and no new card should appear.
2. In the chat, write: "Now run proposal B for 10 minutes too." B's run should not start under the go-ahead you just
   gave. The lead should either ask for a new go-ahead (a new approval card, for B) or tell you the earlier go-ahead
   covers only A. Approve the new card, and B's run should start.
3. Ask for a coding workspace for proposal A, naming A in the request, and approve it. Let the workspace build for
   more than an hour. When the coding agent submits, the validation of its submission should start without asking you
   again: the go-ahead lasts while its workspace is running.
4. An approval you gave before this change, if the campaign has one with time left, still covers any proposal's work,
   as it did before.
