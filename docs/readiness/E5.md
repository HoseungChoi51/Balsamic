# E5 — Adoption happens by itself after an install

State: implemented and tested (PR pending, 2026-10-27); not checked live.

## What was wrong

Layer: none. A step someone had to ask for: after E4, a campaign's tasks adopted an installed library's problem only when the
researcher or the lead sent `campaign.adopt_problem`, so the library written for a declared charter sat unused until someone
remembered to ask.
Invariant: INV-E5-1 (added), INV-B4-1 (updated).

## What changed

| Change | Where |
|---|---|
| `adopt_provided(workspace, install)`: when the install provides the problem its campaign's charter declares, the declared tasks adopt it through the bus as Balsamic's system actor, citing the install (`campaign.adopt_problem`, command id from the install and campaign) | `agents/library_install.py` |
| It runs first in the post-install step: `after_install()` adopts, then binds (B4), then launches (B5) | `agents/library_install.py` `after_install()` |
| Only when no declared task has a bound evaluator or live runs (queued, running, pausing, paused, stopping): `Workspace.unused()` says why not. The same check refuses a `campaign.adopt_problem` from the system actor itself, whatever calls it; the researcher and the lead are not held by it | `execution/service.py` `unused()`, `adopt_library_problem()` |
| Otherwise adoption is skipped and the install notice tells the lead why, naming `campaign.adopt_problem` and the install id; when it adopts, the notice says how many tasks did | `agents/library_install.py` `adoption_text()`, `Installer.install()` |
| The install record lists `adopted` (old task, new task) or `adoption_skipped` (problem, reason) | `library_install` records |
| `campaign.adopt_problem` joins `SYSTEM_OPERATIONS` | `campaigns/commands.py` |
| New row INV-E5-1; INV-B4-1 names the system actor's second operation | `docs/invariants.md` |
| The plug-in guide's install section describes it | `docs/optimizer-plugins.md` |

## Checked

- `tests/test_automatic_adoption.py`: an install adopts a task with no evaluator and no live runs, by a receipt whose actor
  and origin are `balsamic` citing the install, and replaying it adopts nothing more; a task with a queued, running or
  paused run is not adopted, the reason is recorded and the notice names `campaign.adopt_problem`, which the lead then uses
  to adopt it (the run keeps its task); a task with a bound evaluator is not adopted, and the system actor's own command
  is refused; an install that provides no declared problem adopts nothing; the real install path (a problem library
  installed for a declared charter) adopts and its notice says so.
- `tests/test_automatic_binding.py`: the system actor still runs no other operation.
- Full suite (see the PR for the counts).

## Not done

- The adoption covers the install's own campaign: another campaign whose charter declares the same problem is not adopted
  by itself; its lead can use `campaign.adopt_problem` with the install id.
- Not checked live.

## Acceptance test

Needs a coding workspace that delivers the library for a campaign whose charter declares its problem.

1. Start the app and open a campaign whose charter declares a problem to be built (for example baking order), with no
   evaluator commissioned for it and no runs yet. Have its coding agent deliver the library that provides that problem.
2. When Balsamic installs it, the install notice in the chat should end with "Balsamic had 1 task adopt its problem." The
   campaign's task now runs the installed problem, and nothing asks for an evaluator to be commissioned.
3. In a campaign whose declared task already has an evaluator attached (as baking order's has), deliver and install the
   library. The notice should say Balsamic did not adopt the problem because the task has a bound evaluator, and name
   `campaign.adopt_problem`; the same happens while a run on the task is still going. Ask the lead to adopt it: it should,
   and a running run carries on.
