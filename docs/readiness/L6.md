# L6 — Method libraries split off when a second problem needs them

State: merged (#108, 2026-10-28), released in `track-l` ([notes](../releases/track-l.md)); not checked live (see the acceptance test).

## What was wrong

Layer: evidence. After L5 a general method of one problem's library could be bound in a campaign on another problem, and it
stayed in the first problem's library, whose versions then decided a method another problem relied on.
Invariant: INV-L6-1, INV-L6-2, INV-L6-3 (added).

## What changed

| Change | Where |
|---|---|
| Binding or running a problem library's method on a task whose problem that package does not provide records a `library_split` (the method, its library and package, the problems and campaigns needing it) and tells the lead once; the method list shows the split as the next step | `agents/library_split.py`; `implementations/builtin.py` `bind()`; `campaigns/commands.py` (trial.create); `campaigns/method_catalog.py` `catalog()` |
| `implementation_workspace_create` takes `split`: the workspace starts from the problem library's latest version, and TASK.md's "The split" asks for `libraries/<library>-methods/` with the methods and no problem, and the problem library's next version without them that depends on it | `agents/development.py` `WorkspaceCreate.split`, `split_of()`, `split_library()`; `agents/development_ticket.py` `split_lines()`; `agents/tools.py` |
| A split delivery is installed as one step: the method library is validated first (it provides the split's methods and no problem, takes over no other method, its moved methods pass and replay their recorded runs), then the problem library with the method library importable beside it (`/dependencies` in the sandbox); a moved method counts as kept; both are committed to their repositories, pinned, synced with one `uv lock`/`uv sync`, tagged and recorded, or neither is. The problem library's version records `depends_on` and `moved`, and the split is done | `agents/library_install.py` `Installer.plan()`, `_validate_split()`, `install()`; `agents/library_validation.py` `run()`; `agents/library_repository.py` `record()` |
| The Packages page marks a method package, says which package depends on which, and a version's moved methods | `agents/library_repository.py` `catalog()`, `detail()`; `frontend/src/packages/PackagesPage.tsx` |

## Checked

- `tests/test_library_split.py`: a binding on a second problem records the split and tells the lead once, the method list
  names it, a run on the same problem adds nothing, a method on its own library's problem or a bundled one needs no split; a
  split workspace starts from the problem library's latest version and its ticket asks for both libraries; a split installs both
  at once (method library first, the problem library validated with it importable), the method moves and counts as kept, both
  versions are recorded with the dependency, the Packages API shows it; a method library that takes over an unnamed method, a
  problem library that does not depend on it, and a delivery of one library are refused with the lab unchanged.
- `frontend/tests/packages.spec.ts`: the method package, the dependency and the moved methods.
- Full runs at the PR's head: see the PR.

## Not done

- A method only one problem's campaigns use stays in its problem library (decision 26); nothing splits until a second problem
  needs it.
- The split's ticket asks the coding agent to write the method library; Balsamic does not move the code itself.
- uv's resolution of the problem library's path dependency on the method library is checked by the real `uv lock` at install,
  not by these tests, which fake uv.

## Acceptance test

1. Bind a method of problem A's package in a campaign on problem B.
2. The lead is told the method is now needed by a second problem, and the method list shows the split as the next step.
3. Approve the split workspace. When it delivers, the Packages page shows a new method package with the method, and A's
   package's new version depends on it; runs in both campaigns still use the method.
