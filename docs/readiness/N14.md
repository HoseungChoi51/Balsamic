# N14 — Size ladders

State: implemented and tested (PR to be opened, 2026-10-28); the acceptance test below is Hoseung's.

## What was wrong

Layer: evidence. A comparison was per task. Exact methods win on small instances and run out of budget on large ones,
and where that happens (the crossover) is often the finding, but nothing reported it; and "Extend" on a method that had
already finished on its own offered more budget, which changes nothing.
Invariant: INV-N14-1, INV-N14-2 (added, in `docs/invariants/N14.md`).

## What changed

| Change | Where |
|---|---|
| A charter instance may name its `size`: a number or integer quantity whose value grows across the instances, the same one in every instance (findings `instance.size_mixed` and `instance.size_unknown` block confirmation otherwise). Each compiled setup and its task record `size: {name, value}`. Unset, the field is left out of every dump, so charters, setups and tasks made before this part keep their bytes | `contracts/problem_charter.py` `Instance`, `contracts/problems.py` `ProblemSize`, `contracts/problem_imports.py` `ProblemSetup`, `contracts/requests.py` `TaskInput`; `problem_charter/charter.py` `findings()`, `compile_setups()` |

| The comparison report adds `size_ladders` when its groups sit on two or more sizes: per method whether it finishes on its own or runs to its budget, the sizes it finished at and the largest; per pair of methods the leader at each size (better mean at the group's matched cost) and the crossovers. Methods are matched across sizes by their identity without the schedule. Reports with no ladder are unchanged | `analysis/general.py` `size_ladders()`, `report()` |

## Checked

- `tests/balsamic/test_size_ladders.py` (6 tests): three sizes of the continuous benchmark, a fixture exact method that
  finishes on the first two and runs out of budget on the third, and a heuristic: the report names the exact method's
  largest finished size (3), the heuristic's (4) and the crossover at size 4; "Extend" on the exact strategy after it
  finished on size 2 proposes size 3, sending it starts a new run on that task, and after size 3 it proposes 4; a heuristic
  that runs to its budget gets no next size; a campaign with no ladder reports per task with no `size_ladders`; records
  without a size dump without one; a charter's sized instances compile to sized setups and tasks, and mixed or unknown
  sizes are findings; a pack's size ladder must name one growing key.
- `frontend/tests/size-ladder.spec.ts` (Playwright): the button, the explanation and the task sent with the allocation.
- The full suite (counts in the PR).

## Not done

- Change 4 of the roadmap entry, the race climbing a size ladder, is not built. The adaptive race still needs MEENT's
  objectives for an eligible endpoint (N5's Not done), so it races only MEENT, and MEENT declares no size ladder: a climb
  could not run or be tested on any installed problem. The pack's `sizes` are the declaration a later climb reads.
- "Extend" proposes only sizes the campaign already has as tasks; adding a task at the pack's next size is a campaign
  change left to the researcher.
- "Deterministic" is read from the task's evaluator (a declared problem's manifest; installed problems count as
  deterministic); a method's own determinism is not declared anywhere yet.
- The comparison's ladder is in the report and the agent's brief; no page draws it yet.

## Acceptance test

1. Write or edit a problem note whose charter has two or three instances that differ in scale (for example 8, 12 and 20
   jobs), each naming the same `size`. If one instance leaves the size out, the Charter page shows a blocking finding
   asking to name it in every instance or none.
2. Confirm the charter and run an exact strategy and a heuristic on every instance. Ask the lead to compare at matched
   cost (/compare): its answer names, for the two methods, the largest size each finished at and the size where the
   heuristic overtakes the exact method.
3. On the Evolution page, select the exact strategy after it finished on the smallest instance. The action button reads
   "Run on the next size…"; open it: it says more time would change nothing and names the next instance. Run it: a new
   run starts on that instance. A heuristic selected alone still shows "Allocate time…".
