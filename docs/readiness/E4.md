# E4 — Tasks adopt a library's problem

State: implemented and tested (PR pending, 2026-10-27); not checked live.

## What was wrong

Once a library providing a charter's declared problem was installed, compiling the charter again gave installed setups (E3),
but a campaign's existing tasks kept their declared problem and its evaluator requirement: `commissioning.readiness()` still
wanted a validated evaluator for them, so the very library written for the charter could not be used by the campaign.
Revising the campaign was the only way through, and it archives every task and marks every run's charter superseded.

Layer: none. A new capability: nothing let a campaign's tasks take up an installed library's problem.
Invariant: INV-E4-1 (added).

## What changed

| Change | Where |
|---|---|
| `Workspace.adopt_library_problem(campaign_id, install_id, *, authority)`: when an installed library provides the problem the campaign's confirmed charter declares, the tasks are compiled again from the charter and each declared task is replaced by a new task (same name, configuration and fidelity, the installed problem). One campaign version and one new study (child of the active one) for the whole adoption. Refused, changing nothing, when the install is not installed, does not provide the declared problem, or the lab's registry does not see it (the charter still compiles it as declared) | `execution/service.py` |
| The new task records `provided_by` (package, version, commit, submission, install). The old task is kept as it was, never rebound: archived, with `superseded_by_task_id`. A new immutable `evaluator_requirement_satisfaction` record links the old evaluator requirement to the install (and to both tasks) | `execution/service.py` |
| Adopting the same install again finds no declared task left and changes nothing (no version, no study, no record) | `execution/service.py` |
| `current_tasks()` leaves superseded tasks out, so binding (B4) and launching (B5) work on the new task | `execution/service.py` |
| New command `campaign.adopt_problem` (`install_id`, `rationale`), for the researcher or the lead (delegated; it starts no compute), mandate class `implement`; the lead's `campaign_command` lists it | `contracts/commands.py` `ProblemAdoptionInput`, `campaigns/commands.py`, `campaigns/mandates.py`, `agents/tools.py` |
| `_add_tasks()` returns the task records it wrote | `execution/service.py` |
| The install section of the plug-in guide describes adoption | `docs/optimizer-plugins.md` |
| New invariant row INV-E4-1 | `docs/invariants.md` |

The §4 risk (archived declared tasks re-validated through `TaskInput`): the only `TaskInput` validation of stored tasks is
`_from_charter()`, which maps compiled setups onto current tasks by name; a superseded task is not current, so it is never
re-validated. A later revision of the charter after an adoption is tested.

## Checked

- `tests/test_problem_adoption.py`: adopting creates a new task with `provided_by`, the installed problem and the old task's
  configuration and fidelity, supersedes the old one (kept with its manifest and requirement), records the satisfaction,
  bumps the campaign version once and opens one study whose parent is the old active study, and the new task needs no
  commissioned evaluator; adopting the same install again (by command or directly) changes nothing; a superseded task is
  not in `current_tasks()` even if it were not archived, and revising the charter afterwards compiles the installed
  problem; the lead can adopt; an install that provides another problem, or failed, is refused; without the library in
  the registry nothing is adopted.
- `tests/test_mandates.py` (every operation has a class), the command, charter and install tests.
- Full suite (see the PR for the counts).

## Not done

- Adoption is not automatic: E5 runs it after an install when the old task has no bound evaluator and no live runs.
- Runs still going on a superseded task go on; they keep their task id.
- No page has a button for it: the researcher asks the lead, or a client sends the command.
- Not checked live.

## Acceptance test

Needs a problem library installed for a declared charter (E2 makes that possible).

1. Start the app and open a campaign whose charter declares a problem to be built (for example baking order), and whose
   coding agent has delivered and installed the library that provides it under the same problem id.
2. In the campaign's chat, ask the lead: "The library is installed; have the campaign's tasks use its problem."
3. The lead should say it adopted the library's problem: the task now runs the installed problem, named after the
   library's package and version. The campaign's revision goes up by one, and nothing asks for an evaluator to be
   commissioned for that task any more.
4. Ask the lead to do it again. It should say there was nothing left to adopt, and the campaign's revision should not change.
