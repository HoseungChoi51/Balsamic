# L5 — Reuse first

State: implemented and tested (PR on branch `claude/project-thread-fcyj4d`, 2026-10-28); not checked live (see the acceptance test).

## What was wrong

Layer: mandate. The lead could open coding work for a method the lab already had, binding an installed method was `implement`
work that Explore refused, so it needed a go-ahead, and strategy entries carried no code.
Invariant: INV-L5-1, INV-L5-2, INV-L5-3 (added).

## What changed

| Change | Where |
|---|---|
| The method list names each method's package and version: the Algorithms list says "package <name> <version>", and `campaign_inspect`'s methods carry `package` | `campaigns/method_catalog.py` `package_of()`, `catalog()`; `agents/tools.py` `methods()`; `frontend/src/hypotheses/Implementations.tsx` |
| An agent opening a coding workspace for proposals whose named method is installed and runs on a current task is refused, naming the method, its package and the task, with the binding to make instead; reuse needs no coding time. A proposal that names a new method opens one as before | `agents/development.py` `reuse_first()`; `campaigns/method_catalog.py` `reusable()` |
| `implementation.bind_builtin` and `library.apply` are the class `reuse`, which Explore and Screen allow without a card (decision 27); a mandate recorded before L5 allows it too | `campaigns/mandates.py` `CLASSES`, `require()`; `contracts/mandates.py` |
| `library.publish` records the winner's code (`code`: package, version, method, library version). `library.apply` of a winning entry binds the new proposal to its method when it is installed and runs on a current task (noting when the lab runs another version), and says when it is not installed | `balsamic/library/service.py` `code_of()`, `_bound()`, `apply()` |
| The Library page shows an entry's code, and the apply dialog says it is bound when the lab has it | `frontend/src/library/LibraryPage.tsx` |

## Checked

- `tests/test_library_reuse.py`: the catalog and `campaign_inspect` name a package method's package and version; an agent's
  workspace for a proposal naming an installed, runnable method is refused with the binding, one naming a new method opens,
  the researcher's opens; under Explore reuse passes and a workspace does not, a pre-L5 mandate allows reuse; an entry records
  its code, applying it binds the proposal and notes the lab's version, and an entry whose method is missing says so.
- `frontend/tests/library.spec.ts`, `implementations.spec.ts`: the entry's code and the dialog; "package" on the Algorithms list.
- Full runs at the PR's head: see the PR.

## Not done

- A proposal an agent applies still needs its concept review before it runs, as every agent-made proposal does; the
  researcher's apply runs at once.
- A method of another problem's package is bound only where it runs on the task's problem; splitting it into a method package
  is L6.

## Acceptance test

1. Open the Hypotheses page's Algorithms list: each method from a package names the package and its version.
2. In a campaign whose request has no go-ahead (Explore), ask the lead to try an installed method that fits the task. It
   binds the method without an approval card and says reusing it needs no coding time.
3. Publish a winning strategy to the Library, then apply it in another campaign on the same problem: the new proposal is
   bound to the package's method and can run at once.
