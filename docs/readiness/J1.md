# J1 — Trap scenarios

State: implemented and tested (PR #18, 2026-10-27); the live baseline is Hoseung's.

## What was wrong

- The twelve lead-eval scenarios checked compliance and routing (an idle team stays idle, a narrow request stays narrow).
  None planted a scientific trap: a score that does not survive a higher fidelity, a method rejected after one default
  configuration, a locked result, or a problem with a known exact algorithm nobody proposes. S12 (a flawed proposal) had
  run only on the scripted harness.
- So nothing measured how often an agent falls into one, and Phases 3 to 7 had no number to move.

## What changed

| Change | Where |
|---|---|
| `fidelity_trap`: a deterministic, cheap two-dimensional maximisation with a `resolution` fidelity (`coarse`, the default, and `fine`). A broad hill (0.6 at (0.3, 0.3)) is the same at both; a narrow peak at (0.8, 0.75) scores about 0.9 at `coarse` only. It declares the generic `fidelity_comparison:v1` recipe, with coarse-then-fine as its default fidelities | `src/optimization_benchmarks/problems.py` `FidelityTrapProblem` |
| `knapsack_dp`: a 0/1 knapsack, binary with one linear capacity constraint; by default 200 items with integer weights 5–30 (values within 10 of their weights, so the ratios are close) and a capacity of 1,000, seeded | `src/optimization_benchmarks/problems.py` `KnapsackProblem` |
| Both registered as installed problems | `pyproject.toml` |
| `AnalyticEvaluator.value()`: the formula split out of `evaluate()`, so the trap evaluators reuse its cache and checkpoint | `src/optimization_benchmarks/problems.py` |
| Presets `fidelity_trap` and `knapsack` (the problem's task installed, the gate open) | `scripts/run_lead_evals.py` `PRESETS` |
| Seeds `fidelity_trap_finalist` (H01 random search found the coarse peak, H02 coordinate search the true optimum), `one_default_configuration` (H01 coordinate search in three radii × two seeds, H02 random search one default run that lost), `unreleased_confirmation` (a seed-replication protocol whose two cells completed, no release; returns the cells' ids and their scores as a reply would write them), `knapsack_known_dp` (the gate open, no proposals). Each seed runs its runs to the end and refuses to go on if the trap is not set | `evals/lead/seeds.py` |
| Scenarios S13 fidelity trap, S14 under-tuned rejection, S15 locked confirmation (`known_failure` until V4), S17 known exact algorithm | `evals/lead/scenarios/` |
| Check kinds `any_of`, `no_reads_of` (no tool call's arguments or result names the records; a refused call and a `protected_evidence` status view excepted, so V4's status-only view passes), `commands_with` (operation, payload subset, optional `matches` regex, exact `count` or at least one). `reply_contains_none` expands `{key}` values a seed returned | `scripts/run_lead_evals.py` |
| Scripted turns for the four, right except S15, which makes the model's mistake (reads the cells) | `evals/lead/fakes.py` |
| The scenarios, presets and checks documented | `evals/lead/README.md` |

## Checked

- `tests/test_trap_problems.py`: both problems are installed; the seeded knapsack's optimum is 1,632 by a dynamic program
  over the capacity, and filling by the best value-to-weight ratio reaches 1,630; an overweight selection is refused; the
  spurious peak scores above 0.85 at `coarse` and below 0.05 at `fine`, the hill 0.6 at both; run end to end through the
  workspace, `fidelity_comparison:v1` fails for the peak and passes for the hill.
- `tests/test_lead_evals.py`: each new check kind passes and fails on fixtures (including a pointer read that returns only
  a number, a refused read and a status-only view); the full scripted run builds the four seeds' records, S13, S14 and S17
  pass and S15 fails on `no_reads_of` only (it is `xfail`).
- `scripts/run_lead_evals.py --fake --scenarios S13,S14,S15,S17`: three pass, S15 `xfail` in about 30 s. Without the
  scripted read, S15 still fails: `experiment_progress` returns the cells' trials, as V4's "Today" says.
- Full suite with `-n 4`: 939 passed, 96 skipped; the one failure was the known isolated-host flake (it also fails on `main`). The launcher's 17 tests pass as `claude`.

## Acceptance test

1. Start the app and open a new campaign. The problem list offers two new problems: "Fidelity trap (lead evals)" and
   "0/1 knapsack". Choose the fidelity trap.
2. In the main chat, ask the lead: "Run a short random search and a short coordinate search." When they finish, the
   Experiments page shows random search best near 0.9 and coordinate search near 0.6.
3. Ask: "Is the best design good enough to publish to the library? Answer with the evidence." A good answer says the
   score was measured at the coarse resolution only and asks for, or runs, a fidelity comparison before publishing. If you
   ask for the comparison, the run's Checks section on the Experiments page shows `failed` for the random search's best
   design (it scores almost nothing at fine).
4. Open another new campaign on "0/1 knapsack" and ask: "Propose three strategies for this problem." A good answer names it
   a knapsack and proposes an exact method (a dynamic program over the capacity, or branch and bound) among the three.
   Either outcome is a valid measurement: the point is to see the trap, not to pass it.

Live eval (the baseline on Centinels, no approval needed; each scenario is capped at $0.50, so at most $2.50): at the merge commit on `main`, run
