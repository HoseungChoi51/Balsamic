# N5 — Pack estimators and fidelity ladders

State: implemented and tested (PR #49, 2026-10-27); nothing to check live, since MEENT races and forecasts are meant
to behave exactly as before.

## What was wrong

Layer: none: no agent or researcher failure; the domain sat in the core (principle 7, "no domain in the generic path").
Invariant: INV-N5-1 (added), INV-27 (its allowlist shrinks by one file).

The adaptive race and the resource view were MEENT's in the core. The race's default validation ladder `(10,5) → (12,6) →
(14,7)`, its ceiling `(34,17)`, its `+4/+2` step above the search orders, its memory scaling by the squared RCWA harmonic
count and its preferred FLRL methods were constants in `execution/racing.py`. The resource view called
`execution/rcwa_memory.py` (the MEENT 0.13.2 planner) with a 256 × 128 grid written into the call, decided whether to plan
by comparing the task's problem id with `meent_2d_dual_polarization_deflector`, and always added orders 22 to 34 to its
checks. A race on any other problem would have failed on the RCWA keys.

## What changed

| Change | Where |
|---|---|
| The pack's `racing` section gains `step` (how far above the search fidelity to validate when the ladder has nothing higher) and `memory_checks` (orders the memory plan forecasts besides the protocol's). Its fidelities are `{name: int}` and must all name the same keys; a ladder or limit needs a `cost_model`, which names `growth(target, reference)`: how a worker's peak memory grows between two fidelities (it also orders them). The section applies only to a task whose fidelity names those keys. The `memory` estimator's signature is documented | `contracts/packs.py` `PackRacing`, `PackEstimators` |
| `rcwa_memory.py` moves to MEENT's pack unchanged, with an `estimate()` hook that takes the grid from the task's configuration. MEENT's racing values (the same ladder, limit, step, orders to forecast and preferred methods) and its cost model (`(harmonics(target) / harmonics(reference)) ** 2`, the expression the race used) are in `racing.py`, and the pack declares both | `src/dqn_meent/pack/memory.py`, `src/dqn_meent/pack/racing.py`, `src/dqn_meent/pack/__init__.py` |
| `problem_pack()`, `racing_for()`, `task_racing()` and `hook()` find the pack of an installed problem, the racing section that applies to a task, and the callable a hook names | `evaluation/packs.py` |
| A race records the racing section of its task's pack when it is created (`race["racing"]`, `None` without one), so a reinstall mid-race does not change its rules; a race recorded before N5 reads its problem's pack. The validation plan takes the ladder, limit, step and cost model from it; the launch order takes the preferred methods; `_effective_configuration()` overrides whichever fidelity keys the task has | `execution/racing.py` `AdaptiveRacing._racing()`, `create()`, `_final_validation_plan()`, `_tick()` |
| A race without a racing section runs at its task's declared fidelity: its validation plan has status `declared_fidelity` and no ladder, and the race ends with its confirmation (`complete_at_declared_fidelity`) instead of being censored as numerically inconclusive | `execution/racing.py` `_declared_fidelity_plan()`, `_queue_final_validation()` |
| The resource view plans memory for a race whose problem's pack has a racing section for the task's fidelity (not for one problem id), uses the pack's estimator, orders to forecast and cost model, and with no estimator lists the manifest's fidelities with their measured peaks only | `execution/observability.py` `_memory_plan()`, `_plans()` |
| `execution/rcwa_memory.py` leaves N1's allowlist (25 files remain after N8) | `tests/balsamic/test_layering.py` |
| The docs name the planner's new place and the pack's racing section | `docs/resource-observability.md`, `docs/adaptive-algorithm-testing.md` |

## Checked

- `tests/test_pack_racing.py` (19 tests). `tests/fixtures/meent_race_reference.json` was generated by running the
  scenarios on `main` before this change (`6d6bf5b`): eight validation plans (search orders 10, 12, 22, 30 and 34; with
  and without measured samples; the default, a declared and an over-the-limit ladder; a raised validation peak) and three
  resource-view forecasts (16 and 30 GiB available, a small grid with no manifest). With MEENT's pack the plans and
  forecasts are equal field for field, except ids, times and the plan's `prediction_basis` sentence, which now names
  the problem's cost model instead of harmonic counts. Also: a MEENT race records the pack's section and an old race
  reads it; the section applies to RCWA orders only (not `meent_grating`'s `fourier_order`, not `bounded_continuous`);
  a `bounded_continuous` race has no ladder, freezes a `declared_fidelity` plan, ends with its confirmation without
  queueing checks, and launches its cells in declaration order; its memory checks show measured peaks only; racing
  sections with mixed keys, a ladder without a cost model or non-integer orders are refused.
- `tests/test_meent_pack_memory.py` (the planner's tests, moved with it, including the command line that imports neither
  Torch nor MEENT), `tests/test_framework_racing.py` (its tasks now name the 2D problem, as real ones do),
  `tests/test_resource_observability.py` (its race task now has RCWA orders, as real ones do), `tests/test_problem_packs.py`,
  `tests/test_invariants.py`, `tests/balsamic/test_layering.py`.
- The full suite (counts in the PR).

## Not done

- `execution/racing.py` and `execution/observability.py` stay on N1's allowlist: the race's activity gates name FLRL
  algorithms (`flrl_autograd_adam`, `flrl_lsf_es`) and its calibration names the gradient methods, and its endpoints and
  report read MEENT's objectives (`mean_plus1_transmission`, TE, TM); the resource view recognises a `grating-lab`
  process. These belong with N8 (domain optimizers) and a later part for the race's objectives, not with the ladder.
- The race's resource policy (the 5 GiB floor, 4 GiB headroom, one-two-four threads) stays in the core: it is about the
  host, not the problem.
- A race without a ladder measures cost in worker seconds, as every race does; N11 adds the problem's cost axis.
- The pack's `estimators.time` hook is still unused.

## Acceptance test

None: nothing in the app changes. MEENT races validate at the same orders and the resource view forecasts the same memory
as before; a race on a problem without a fidelity ladder, which would have failed before, now ends with its
confirmation. The change shows in `tests/test_pack_racing.py`, whose reference fixture was produced by the code before
this part. If a MEENT 2D adaptive race is running when the release is installed, it should carry on and validate its
finalists at the same orders as it would have before.
