# D3 — Declared problems show their data to methods

State: implemented and tested (PR pending, 2026-10-27); not checked live.

## What was wrong

A method learns about its problem from `descriptor()["public"]`, which holds the configuration keys the problem declares
public. `charter.manifest()` built a declared problem's `EvaluatorManifest` without `public_configuration_keys`, so for
every problem declared in a charter the public descriptor was empty: methods saw none of the instance's data. In baking
order the coding agent hard-coded the due dates into its method instead of reading them.

## What changed

| Change | Where |
|---|---|
| `manifest()` sets `public_configuration_keys` to the configuration fields the charter binds to its evaluator (sorted), so `descriptor()["public"]` carries the instance's data. The fidelity is not listed and stays private | `problem_charter/charter.py` `manifest()` |
| The manifest's digest now includes those keys, so only tasks compiled after the change carry the data. Tasks compiled before keep their stored manifest, digest and empty public descriptor; nothing is migrated | (no code: stored manifests are read as they are) |

## Checked

- `tests/test_public_configuration.py`: a task compiled from a declared charter lists its configuration fields as public,
  `descriptor()["public"]` gives their values and not the fidelity, and a packaged method receives them both in
  `create_optimizer`'s context and in `initialize`; a data table bound to the evaluator (a list of due times) reaches the
  method as that list; a task stored before the change loads back unchanged, keeps its digest (`definition_version`) and an
  empty public descriptor, while a newly compiled one has a new digest.
- `tests/test_problem_charter.py` and `tests/test_permutations.py` pass unchanged; the full suite is in the PR.

## Not done

- Campaigns made before the change keep methods blind to the data until their task is compiled again (a new task from
  the confirmed charter). That is by design (no migration).
- Installed problems are unchanged: they declare their own public descriptor in their adapter.
- Not checked live on the dev stack.

## Acceptance test

1. Start the app and open a campaign whose problem was declared in its charter (no installed evaluator), for example baking
   order, with its data (the bakes' due times and durations) given on the Charter page. If the campaign was made before
   this release, confirm the charter again and make a new task from it so that the task is compiled with this change.
2. Ask the lead for a method written for this problem (a coding workspace), and let it be built and installed.
3. Open the workspace's code or the coding agent's report. The method should read the due times and durations from the
   problem it is given, not have them typed into its code. Ask the lead "what data does a method see for this problem?":
   it should list the configuration values from the charter (the due times and durations), and not the fidelity settings.
4. Change one due time on the Charter page, confirm, and run the same method on the new task. Its results should follow
   the new due time without the method's code being changed.
