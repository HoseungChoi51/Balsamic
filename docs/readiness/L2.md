# L2 — One repository per library, with versions

State: implemented and tested (PR on branch `claude/project-thread-fcyj4d`, 2026-10-28); not checked live (see the acceptance test).

## What was wrong

Layer: evidence. A library had no history: the lab's copy was a folder each delivery overwrote, L1's archive kept loose
copies, and nothing let a campaign name the version it used.
Invariant: INV-L2-1 (added), INV-L2-2 (added), INV-L1-2 (updated: the repository is the archive).

## What changed

| Change | Where |
|---|---|
| One bare Git repository per library on the host, `<data>/library_repositories/<name>.git`, which no box mounts. Git runs as on the host's own-session store (no configuration, hooks or upkeep) | `agents/library_repository.py` `repository()`, `commit()`, `files_at()` |
| An install commits the version's files onto the repository's `main` (the source commit, workspace, campaign and submission in the message), writes the lab's copy from that commit and checks it against what was submitted; once the version is in, it tags it `v<version>` and records a `library_version` (parent, source, methods, problems, what it added and removed). The install records `library_version_id`, `tag` and `library_commit` | `agents/library_install.py` `Installer.install()`, `commit_message()`; `agents/library_repository.py` `publish()`, `record()` |
| The same version with other code is refused by its tag | `agents/library_repository.py` `check_tag()` |
| L1's archive folders and the lab's own copy become a library's first versions, once: when it is installed again, and for libraries committed with the lab when the Packages page lists them | `agents/library_repository.py` `imported()`; `agents/library_install.py` `Installer._import_replaced()`, `import_lab()` |
| `GET /api/libraries` (each library: package, latest version, versions, methods, problems) and `GET /api/libraries/<name>` (versions newest first; each method and problem with the version that brought it, whether the latest has it, and the campaigns that use it) | `agents/development_api.py`; `agents/library_repository.py` `catalog()`, `detail()` |
| The Packages page, a page of the lab in the rail after Library | `frontend/src/packages/PackagesPage.tsx`; `frontend/src/router/pages.json`; `frontend/src/shell/StagePanel.tsx` |
| The roadmap's L2 item 5 (the researcher's own session clones the library) moved to L3, where a workspace has a base version to give | `docs/roadmap/track-l-code-libraries.md` |

## Checked

- `tests/test_library_repository.py`: two installs give tagged commits in one line of history, each version with its parent
  and what it added, and the lab's copy equals the latest tag; the same version with other code is refused; L1's archive and
  the lab's copy are imported once; the API lists versions, methods and the campaigns using each.
- `tests/test_library_keep.py`: the replaced and new versions are in the repository (was: in L1's folders).
- `frontend/tests/packages.spec.ts`: the page lists a package, its methods with the campaigns using them, and its versions.
- Full runs at the PR's head: see the PR.

## Not done

- A version records the methods it has; which version a run ran is still read from the run's package versions (provenance),
  not linked to the `library_version`.
- Nothing prunes the repositories.

## Acceptance test

1. After two installs of the same package (from two campaigns, or two deliveries), open the Packages page in the rail.
2. The package is listed with its latest version, how many versions and methods it has, and its problems. Open
   "Versions and methods".
3. Each method lists the campaigns that use it; a method a later version removed says "removed".
4. The versions are listed newest first, each with its commit, what it added and removed, and the campaign and workspace it
   came from.
5. The page is the same whichever campaign it is opened from. A package committed with the lab (grating-mask-search) is
   listed too, imported from the lab's copy.
